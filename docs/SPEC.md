# Shipkeep Technical Specification

Status: draft for MVP (v0.1). This document is the contract the code implements. When code and spec disagree, fix one of them in the same PR.

## 1. Glossary

| Term             | Meaning                                                                                                                                |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Organization     | Tenant. Owns members, projects, servers, billing.                                                                                      |
| Project          | Group of environments for one product or one client.                                                                                   |
| Environment      | Isolated deployment target inside a project (`production`, `staging`, previews). Has its own variables, secrets, domains and policies. |
| Node             | A server running `shipkeep-agent`, enrolled in one organization.                                                                       |
| Application      | A deployable unit built from git, an image or a Compose file.                                                                          |
| Service          | One container definition inside a Compose application.                                                                                 |
| Release          | Immutable combination of an image digest and a resolved configuration.                                                                 |
| Deployment       | The process that turns a release into running allocations.                                                                             |
| Allocation       | One running instance of a release (or of a database) on one node.                                                                      |
| Managed database | PostgreSQL, MySQL, MariaDB, MongoDB or Redis run and backed up by Shipkeep.                                                            |
| Action           | A typed command sent from the control plane to an agent.                                                                               |
| Lease            | Time-bound right of a node to run its allocations, with a fencing epoch.                                                               |

## 2. `shipkeep.yml`

### 2.1 Example

```yaml
version: 1
name: billing-api

build:
  type: dockerfile # dockerfile | railpack | nixpacks | image
  context: .
  dockerfile: Dockerfile
  args:
    NODE_ENV: production
  # image: ghcr.io/acme/billing:1.4.2   # only when type = image

run:
  command: ['node', 'dist/main.js'] # argv array only, never a shell string
  port: 3000
  healthcheck:
    path: /health
    interval: 5s
    timeout: 3s
    start_period: 20s
    healthy_threshold: 2

release:
  command: ['node', 'dist/migrate.js'] # runs once per release before the switch
  timeout: 10m

resources:
  cpu: '0.5'
  memory: 512Mi
  disk: 2Gi # what the container may write to its own filesystem (ADR 0022)

scale:
  replicas: 2
  placement:
    spread: node # node | none
    labels: { region: eu }
    nodes: [] # optional explicit node names

domains:
  - api.acme.com

env: # non-secret values only
  LOG_LEVEL: info

secrets: # names only; values set in UI, CLI or API
  - DATABASE_URL
  - STRIPE_KEY

volumes:
  - name: uploads
    path: /app/uploads
    backup: { schedule: '0 3 * * *', keep: 14 }

databases:
  - ref: billing-db # managed database in the same environment
    env: DATABASE_URL # inject the connection string as this secret

previews:
  enabled: true
  ttl: 72h
  max_active: 5
  database: clone # none | empty | clone

deploy:
  strategy: rolling # rolling | recreate
  drain_timeout: 30s
  keep_images: 5
```

      port: 8080

### 2.2 Rules

- Validated against `packages/config-schema/shipkeep.schema.json` (JSON Schema 2020-12). Unknown keys are errors.
- Both validators (`packages/config-schema` and `lib/config`) then refuse well-formed values that could never be deployed, so that saving them fails instead of every later deployment. The shared fixtures keep the two in step.
  - `resources.cpu` above 256 CPUs and `resources.memory` above `1Ti`: the agent refuses more (section 3.3).
  - `resources.memory` below `6Mi`: Docker refuses less.
  - A duration the pipeline reads (`run.healthcheck.interval`, `timeout` and `start_period`, `release.timeout`, `deploy.drain_timeout`) that is too long to be counted.
- `name`: `^[a-z][a-z0-9-]{1,38}[a-z0-9]$`.
- `run.command`, `release.command`: arrays of strings, max 64 items, each max 4096 bytes. No shell is ever implied.
- Durations: Go-style (`30s`, `10m`, `72h`). Sizes: Kubernetes-style (`512Mi`, `2Gi`).
- `resources` is the CPU and memory limit of each container of the application, and what placement reserves for each replica (section 6).
  - A limit left out is `1` CPU, or `512Mi` of memory: an application without `resources` runs under one CPU and 512 MiB. `DEFAULT_RESOURCES` in `packages/config-schema` holds the two values for the control plane and the UI.
  - Zero is refused, in any notation (`0`, `0.0`, `0m`, `0Mi`): no value means "unlimited". A positive CPU amount below one millicore counts as one millicore.
  - `disk` (default `1Gi`, between `64Mi` and `1Ti`) is the size each container's writable layer may reach. It is not reserved by placement. The agent measures it and stops a container above it, with the reason `disk_limit` (ADR 0022).
  - `run.read_only_root: true` runs each container with a read-only root filesystem and a `64Mi` tmpfs at `/tmp`, which counts in its memory: it then writes only there and to its volumes. Off by default.
  - The release task runs under the same limits. It needs no reservation of its own: it runs on the first replica's node before that replica starts, in the room already reserved for it.
- The control plane refuses what the schema describes but no deployment applies yet, on save and again on deploy (`unsupported_config_field`, with the field's JSON pointer), rather than ignore it: a volume that is not mounted would lose what the application writes there at its next deployment. Refused for now: a non-empty `volumes` or `databases`, `previews` unless `enabled: false`, `deploy.strategy: recreate` (every deployment is rolling), and `deploy.keep_images`. Each is accepted again when the feature that applies it lands.
- Domains: valid hostnames, max 50 per app, wildcard only with DNS-01 configured.
- Volume paths: absolute, no `..`, not under `/proc`, `/sys`, `/dev`, `/etc`, `/var/run`.
- Compose files are parsed and validated by the control plane, as an allow list that fails closed: a key is translated to what the typed `ContainerSpec` can express, ignored with a warning when it has no effect on safety (`container_name`, `hostname`, `networks`, `logging`), or refused with its reason.
  - Refused among others: `privileged` (even `false`), `pid`, `ipc`, `uts`, `userns_mode`, every `network_mode`, `cap_add` beyond an allow list (`NET_BIND_SERVICE`, `CHOWN`, `SETUID`, `SETGID`), `cap_drop`, `devices`, `security_opt` other than `no-new-privileges` (which the agent always sets), `entrypoint`, `build`, `env_file`, volume and network drivers or `external`.
  - All bind mounts are refused, including inside the application's data directory and the Docker socket: `ContainerSpec` mounts only named volumes and tmpfs. Use named volumes declared under `volumes`.
  - Commands are argv. A string is split only when it holds no shell character, and is otherwise refused.
  - Ports keep only the container port: nothing is published on the host, and `expose` routes traffic. A publication is reported as a warning.
  - `${NAME}` is expanded only in `environment`, and names the secrets the service needs. Bare names that would inherit from the host are refused.
  - Health checks are probed over HTTP or TCP and no command ever runs. A `curl` or `wget` against localhost is read for its URL; any other check is dropped with a warning.
- Secrets referenced but not set block the deployment with a clear error.

## 3. Agent protocol

### 3.1 Transport

- gRPC over HTTP/2 with mTLS. The control plane exposes `AgentGatewayService` on a dedicated port (default 7443). Names follow buf's STANDARD lint rules (`<Rpc>Request` / `<Rpc>Response`, `Service` suffix).
- The gateway uses TLS 1.3 with a distinct server-auth leaf certificate signed by the installation CA. `AGENT_GATEWAY_SERVER_NAME` sets its DNS or IP SAN; the leaf key stays in memory and is refreshed daily. Only `Enroll` permits an absent client certificate. Other RPCs require a TLS-verified client-auth certificate and a current database registration matching its SPIFFE organization and node. Identity headers are ignored. The gateway caps messages at 64 KiB, unary requested deadlines at 30 seconds and streaming requested deadlines at 24 hours. Streams require a matching node/epoch `Hello` first, then a heartbeat at least every 15 seconds (recommended interval: 5 seconds). One active stream per node replaces its predecessor. Credentials are checked at every frame and at least once per second during silence; authentication/database failures close the stream. After Hello, the stream accepts Heartbeat and ActionUpdate frames. Welcome does not grant a durable lease yet (M4.5).

Action delivery (M1.4a2):

- Actions are queued per node in `agent_actions`. That table is under tenant RLS, with a composite key to the node and an idempotency key unique per node. The action message is encrypted per organization and bound to the action id.
- Every stream sends each unfinished action of its node once, at most every second, so a reconnection redelivers everything unfinished. The agent journal replays known idempotency keys.
- Overdue actions become `expired`.
- An agent update changes only its own node's non-terminal actions; terminal states never change again.
- An action the deployment pipeline enqueues records its application and deployment. Both columns are null for other actions. A composite foreign key ties them to a deployment of the same organization and application; deleting the deployment clears them and keeps the action in the node's history.
- An action's history shows a summary, never its raw report: the agent's fixed error texts become reason codes, and a failure refused before anything ran (malformed request, unknown kind, stale lease epoch, invalid input, conflicting idempotency key) is `refused`. Any other text becomes `unknown`. Results keep only validated fields: container id, image digest, health and release exit code.
- Audit: queueing (`fleet.action.queued`) and every terminal state (`fleet.action.<state>`, with the node as actor).
- The agent calls `Connect(stream ConnectRequest) returns (stream ConnectResponse)` and keeps it open. It waits at most 10 seconds for Welcome and uses the advertised heartbeat interval (1–10 seconds supported). Outage retries use exponential backoff with jitter (0.5 seconds initially, capped at 30 seconds); a minute-long healthy session resets the backoff. TLS keepalive detects dead connections. A rejected identity or epoch stops connection attempts and requires operator recovery; it never triggers automatic re-enrollment. Renewal persists the new credential generation before reconnecting.
- `ConnectRequest` (agent to control plane) carries one of: `Hello`, `Heartbeat`, `ActionUpdate`, `StateReport`, `MetricsReport`.
- `ConnectResponse` (control plane to agent) carries one of: `Welcome`, `ActionRequest`, `CancelAction`, `RoutingTable`, `PeerList`, `LeaseRenewal`, `ConfigUpdate`.
- Metrics go through this stream as `MetricsReport` (ADR 0024, section 12): the control plane labels them and writes them to VictoriaMetrics. Logs do not: they use a third RPC, below.
- Every `ActionRequest` carries `action_id` (UUIDv7), `idempotency_key`, `deadline`, `lease_epoch` and exactly one action in a `oneof`.
- Logs use `ShipLogs(stream ShipLogsRequest) returns (stream ShipLogsResponse)` (ADR 0029, section 12), opened after Welcome when it says logs are kept. Its first frame carries the lease epoch; then come batches of at most 256 entries and 60 KiB, each acknowledged by its sequence number once VictoriaLogs accepted it, at most four unacknowledged. It is authenticated like `Connect`, and one stream per node replaces its predecessor. The node's credential and lease epoch are checked again before each batch and every 10 seconds without one, so revocation, removal or a new lease ends the stream; a stream without `LogsOpen` within 30 seconds ends too. A batch's delivery ends with its stream, replaced, cancelled or the control plane stopping (which ends every agent connection): its wait for the quota and its write to VictoriaLogs stop; its lookup of the node's containers runs to its end, then nothing is written. Nothing is acknowledged after the stream ended: a batch written as it ended is sent again by the agent from its cursor, and searches drop the repeated lines. A delivery that waited for its quota checks the credential and lease again before writing. A node has at most 2 deliveries under way, across its streams. Across nodes, the control plane holds at most 1024 batches waiting for their quota and looks up and writes at most 256 at once, so a node within its rate never waits behind the others. A batch past a bound, or one that would wait more than 10 seconds for its quota, is refused at once (`UNAVAILABLE`) and charged nothing; a batch charged stays charged even if its stream ends, so reconnecting never resets the rate.
- Interactive exec uses a second RPC: when the agent receives `ExecSession`, it opens `ExecStream(stream ExecStreamRequest) returns (stream ExecStreamResponse)` tagged with the `session_id`, carrying stdin, stdout, stderr, resize and exit frames. Browsers reach it through a WebSocket endpoint on the API (`/api/v1/exec/{session_id}`), authenticated and RBAC-checked; the API only relays frames.
  - The stream's first frame is `ExecOpen`, within 10 seconds of the stream's opening (`DEADLINE_EXCEEDED` past that, `CANCELED` if the transport ends first); anything else is `INVALID_ARGUMENT`. A session that is not this node's is refused at once. The node's credential is then checked again before it joins, within the same 10 seconds: one removed or revoked meanwhile gets `UNAUTHENTICATED` and joins nothing, and a store that cannot tell answers `UNAVAILABLE`, the session left to a new stream. Its session must be one the API process opened for this node of this organization, not joined yet: otherwise `NOT_FOUND`, the same answer whatever the reason.
  - The agent and the person who opened the session each join once, within a minute of its opening, or it ends as `not_joined`. Output reaches the browser once both joined; the browser's frames wait for the agent, at most 256, past which the session ends as `flooded`.
  - It ends at the agent's exit or error frame (its fixed text gives `time_limit`, `closed` or `failed`), when either side leaves (`agent_left`, `browser_left`), or on a frame out of order (`failed`). Unless the command exited, the last frame to the agent is `ExecClose{kill: true}`. Whatever the end, the browser's frames still waiting are dropped, never sent: after a sign-out, a loss of `container.exec` or a browser that left, input typed earlier does not run before the command is stopped.
  - The node's credential is checked again every 10 seconds, as for `Connect`: a node removed or revoked loses its sessions (`agent_left`). A session the agent did not end 30 seconds past its time limit is ended by the control plane (`time_limit`).
  - Audit: `exec.session.ended`, with the session's person as actor, the reason, the exit code (null unless it exited) and the duration. The end comes from a connection, not a request: the connections are released at once, and a failed write is tried again, the delay doubling from 1 s to 1 min for about 15 minutes, logged with identifiers and the error's kind only. A retry first looks for the event, so a write whose answer was lost is not recorded twice (issue #489).
  - Every session's check is queued with its opening, in the same transaction, for 5 minutes after the time it must end. If neither `exec.session.ended` nor `exec.session.interrupted` is recorded by then, it records `exec.session.interrupted` (system actor, the session's person and `reason: unknown`): its process stopped, or its end could not be written. A session lives in one API process only, so at start the control plane runs the checks still queued at once, before it listens.
  - The browser joins with a WebSocket on `/api/v1/exec/{id}`: the request must come from the interface's own origin (`Origin` equal to `API_PUBLIC_URL`, not `Sec-Fetch-Site: cross-site`) with a valid sign-in cookie, or `401`; then the session must be this person's, not joined by a browser yet, and they must still hold `container.exec` on its environment, or `404`, whatever the reason; the session is checked again right before the upgrade, so a join overtaken by another one is refused over HTTP too. A client with 20 failed sign-ins in a minute gets `429` before any lookup; the client is the address the trusted proxy forwarded (`TRUST_PROXY`, read as Express reads it), so one browser's failures never refuse the others behind Caddy. Messages are at most 64 KiB. To the browser: output as binary messages whose first byte is the stream (1 stdout, 2 stderr), then text `{"type":"exit","code":n}` or `{"type":"end","reason":…}` with the reason only, never the agent's text. From the browser: binary messages are stdin; text `{"type":"resize","cols":n,"rows":n}` (1 to 1000) or `{"type":"close","kill":true|false}`, with exactly those keys, each a primitive, checked before the `class-validator` DTOs see them; anything else is ignored. A message that cannot be read ends only its own session (`failed`), never the process. Every minute the sign-in and the permission are checked again: signing out or a password change ends the session (`signed_out`), and losing `container.exec` ends it (`access_removed`); a failure of the store ends nothing. The browser is pinged every 30 seconds, and one that misses its pong is gone (`browser_left`). Whatever ends the session, the browser gets `{"type":"end","reason":…}` before the close, unless the exit or the agent's error said it already. When the API stops, it ends every session, joined or still waiting for a side, with `shutdown`, and waits up to 5 seconds for their audit events.

### 3.2 Enrollment

- `Enroll(EnrollRequest{join_token, csr_pem, facts}) returns EnrollResponse{cert_pem, ca_pem, node_id, wireguard_ip, lease_epoch, confirmation_public_key}`. Unary call, server-side TLS only (no client cert yet).
- Trust on first contact: the install command shown in the UI contains the SHA-256 fingerprint of the installation CA (`--ca-fingerprint`). The join-token response also carries `gatewayAddress` (`AGENT_GATEWAY_SERVER_NAME` with the gateway port) for the agent's `control_plane.address`; the web UI shows the token once and the agent configuration without it. Before sending the join token, the agent checks that the gateway's certificate chains to a CA with that fingerprint, then pins that CA. The gateway sends its leaf and CA chain during TLS. A payload-free TLS probe verifies the SHA-256 root pin, server certificate chain, validity and hostname; the enrollment RPC then uses that root with normal TLS verification. Only explicit development mode permits a missing initial fingerprint. RPC requests and responses are bounded to 64 KiB, unary calls time out after 30 seconds, and remote error text is never logged.
- One CA per Shipkeep installation (not per organization). The organization is encoded in each certificate's SAN URI and checked on every call.
- Join token: 32 random bytes, stored hashed (SHA-256), single use, 15 min TTL, bound to an organization.
- Enrollment commits the node, certificate, token consumption and audit record in one transaction. A concurrent losing request or an audit failure leaves no orphaned node or certificate.
- Admission (#346), in the gateway's memory and before any database work, in this order:
  - a quota per client network, `AGENT_ENROLLMENTS_PER_MINUTE` attempts per minute (default 20; an IPv4 address, or an IPv6 /64). Every attempt counts, over any number of connections. At most 10,000 networks are tracked at once; beyond that, new networks share one quota until older windows end. A peer without an address uses that shared quota too;
  - the shape of the request: a malformed join token or a certificate request over 8 KiB is refused without opening a transaction;
  - a budget of 4 enrollments at once across every connection, with at most 32 waiting, each for at most 10 seconds.

  A call refused by the quota or the budget gets `RESOURCE_EXHAUSTED` with the fixed text "enrollment is busy, retry later", which says nothing about the token. A malformed request gets the error of its validation, as before: the rejected join token, or `csr_too_large`. Nothing is logged for it. The agent's service restarts after 5 seconds and enrolls again. Authenticated RPCs (`Connect`, `RenewCertificate`) do not count against either limit. Behind Docker's published port, connections from outside keep their address, while connections made on the host itself through Docker's proxy share the address of its bridge.

- Client certificate: Ed25519, 30-day validity, CN = node_id, SAN URI `spiffe://shipkeep/<org_id>/node/<node_id>`. Rotation through `RenewCertificate` at 2/3 of validity. Node and gateway certificates start five minutes before issuance so a node whose clock runs slightly behind accepts them; the 30 days run from issuance. The gateway re-applies its full TLS settings (including the TLS 1.3 minimum) at every certificate refresh. Once a renewal request is sent, the agent finishes it and persists the result even during shutdown, and keeps retrying a failed credential write with bounded backoff instead of discarding the only valid certificate.
- Re-adoption after a restore (#487): a restore from a backup older than a node's last renewal rolls the registry back, and the agent then presents a certificate the CA signed but the registry does not know.
  - The gateway refuses it as any unregistered certificate. When TLS verified it and the registry knows no such serial (a known serial stays refused: revocation and expiry hold), it records it in `node_readoptions` for its node, if the node exists in the certificate's organization and was not removed. Only the latest certificate of a node is kept, with its validity; the first record of a certificate is audited as `fleet.node.readoption_requested` (by the node), and later presentations refresh `last_seen_at` at most once a minute.
  - `GET …/organizations/{organizationId}/node-readoptions` lists them (`node.manage`). `POST …/nodes/{nodeId}/readopt` registers the waiting certificate for that same node after the caller's password and second factor (`node.manage`, session only), revokes the node's other certificates and deletes the request, in one transaction audited as `fleet.node.readopted` with the revoked serials. A request whose certificate expired, a removed node or no request answers `409`.
  - An agent whose certificate the gateway refuses (`Unauthenticated`, `FailedPrecondition`) presents it again every 5 minutes, and never enrolls again; a re-adopted node therefore connects by itself. Agents up to 0.1.0-alpha.7 wait instead, and connect once restarted (`systemctl restart shipkeep-agent`).
- The agent connects to `control_plane.address` and verifies the gateway certificate against its host, the chain and the pinned CA fingerprint. On the machine that hosts the control plane, `control_plane.connect` (a loopback IP literal with a port, nothing else) says where the TCP connection goes instead; the name verified and the pin stay those of `address` (ADR 0021).
- The daemon reads its initial join token from `control_plane.join_token_file`, a regular 0600 file containing the 43-character token and optionally one newline. It never takes the token in argv or YAML. It deletes the token file only after valid credentials are durably saved; subsequent starts use the pinned identity without enrollment. Missing or invalid credentials fail closed in production; an unenrolled development daemon waits for shutdown.
- Agent credentials are stored as one `credentials.json` generation in its private state directory (0700): Ed25519 key, client certificate, pinned CA, node/organization IDs, lease epoch and confirmation public key. The file is 0600, bounded to 64 KiB and validated as a coherent key/identity/CA set before use. Updates sync a temporary file, atomically rename it and sync the directory so renewal cannot leave a new key paired with an old certificate.
- Revocation: the control plane keeps a deny list of certificate serials; existing streams are disconnected within one polling interval (1 second, plus database latency), even without incoming traffic.
- Renewal checks the registered serial, node and organization against the TLS identity. Replacing the certificate, revoking the old serial and recording the audit event share one database transaction; concurrent renewal attempts have one winner. Agents must persist the new certificate and reconnect after renewal. If the response is lost after commit, the old certificate is revoked and the operator must re-enroll the node; recovery without re-enrollment is an open question below.

The agent reaches Docker through `agent/internal/docker`, a minimal typed Engine API client.

- It talks only to the local `unix://` socket, with API version `v1.47` pinned.
- It exposes only the calls the catalog needs.
- Names are path-escaped and request bodies are typed.
- Responses are capped at 1 MiB, and daemon error text is never echoed.
- Networks are matched by exact name, never by id prefix.

Containers are created from the typed create body in `agent/internal/docker`. That body has no field for privileged mode, host namespaces, devices or bind mounts, so none of them can be requested. The agent always sets:

- `no-new-privileges`, a private IPC namespace and an init process;
- the CPU and the memory limit of the spec, at most 256 CPUs and 1 TiB. Both are required: zero would mean unlimited to Docker, so a spec without either is refused, for a replica and for a release task alike. The agent has no default of its own, since placement must have reserved the value it enforces;
- a pids limit (1024 unless specified, at most 65,536);
- the disk budget of the spec (`Resources.disk_bytes`, 64 MiB to 1 TiB, or zero for none from older control planes) as the agent-owned label `sk.disk_bytes`, which labels from the control plane can never set (ADR 0022);
- bounded `json-file` logs;
- added capabilities from the allow-list only.

The agent also enforces these rules:

- Mounts are managed volumes or bounded tmpfs only, at absolute clean paths outside `/proc`, `/sys`, `/dev`, `/etc`, `/var/run` and `/run`.
- Ports are exposed on the Docker network and never published on the host.
- `secrets_as_files` is refused until the tmpfs writer exists. Secret values are only sent to the local daemon as environment variables.
- Start, stop and remove act only on managed containers, referenced by full id or `sk-` name, never by id prefix. They are idempotent: stopping or removing a missing container is done; starting one fails. Removing a container's volumes needs a `container.remove` confirmation for that container, spent in a non-retryable first step. A token without `remove_volumes` is refused.

Routes (`agent/internal/caddy`, ADR 0005) are typed JSON sent to Caddy's admin API on its Unix socket.

- **Configuration:** the agent owns one `shipkeep` server listening on `:80` and `:443`. It creates only the deepest missing configuration level and never calls `/load`, which would also reset the admin endpoint. Each route is the Caddy object `sk-route-<route_id>`: replaced in place with `PATCH /id/…`, or appended.
- **Hosts:** 1–32 lowercase DNS names (a leading `*.` is allowed); IP addresses and `localhost` are refused.
- **Upstreams:** 1–64 private IP `address:port` literals (Docker or WireGuard networks only), with weights 1–100 mapped to weighted round robin.
- **Maintenance (ADR 0025):** a route with `maintenance` has no upstream. Caddy answers every request for its hosts with a `static_response`: the agent's built-in page, status 503, `Retry-After: 120`, `Cache-Control: no-store` and a Content-Security-Policy that allows only the page's own style, by its hash. No text of the page comes from the control plane. The hosts, the TLS mode and switch-then-drain work as for any route, so the requests the replicas were serving finish before the switch succeeds.
- **TLS:** under automatic HTTPS (`TLS_MODE_AUTO_HTTP`, the default) a route matches HTTPS requests only (`"protocol": "https"`), so that plain HTTP on port 80 gets Caddy's redirect to HTTPS; the server listens on both ports, and Caddy inserts its redirects after the last route that matches a host. `TLS_MODE_OFF` adds the hosts to the server's `automatic_https.skip` list, and its route answers plain HTTP. When it checks the Shipkeep server (at start and before every `UpsertRoute`), the agent adds the HTTPS matcher to the routes of older agents whose hosts are not skipped (#342). DNS-01 is refused until a provider is configured.
- **Switch-then-drain:** `UpsertRoute` switches upstreams atomically and, when it replaced an existing route, waits the drain timeout (default 30 s, at most 5 min) before succeeding, so stopping the old instance comes after draining. `RemoveRoute` also drains after removal.

Self-reconciliation (M1.6, `agent/internal/reconcile`):

- **Intent:** the journal records, per managed container, whether it should run. `StartContainer` sets it after starting; `StopContainer` clears it before stopping, so a stopping container is never restarted; `RemoveContainer` forgets it.
- **Every 30 s,** with or without the control plane, the agent starts each managed container that should run but is not running, and records each observation in the journal's actual state. Missing containers are left to the control plane, because their secrets are not stored on the node.
- **Routes (ADR 0017):** an `UpsertRoute` with container upstreams records the route in the journal before Caddy gets it: its upstreams as asked (container and port, or address, with weight) and the dials it is about to hold. The maintenance page and address upstreams record nothing, and `RemoveRoute` forgets the record once Caddy has removed the route. After the containers, each pass resolves every recorded container again: Docker gives a restarted container whatever address is free, and another container may have taken its old one. The route gets the current address of each container that runs, in its order and with its weight; a container that does not run gets no traffic, and a route none of whose containers runs answers 503 until one does. The pass changes a route only while Caddy holds dials the agent recorded, and records the new dials before writing them, so a write cut short is taken up again on the next pass. The route actions and the pass write a route and its record under one lock.
- **Facts:** `CollectFacts` reports hostname, OS, kernel, architecture, CPU count, memory (`/proc/meminfo`), state-directory disk size and free space, the Docker version and the agent version, without running any command.

Certificates (PLAN M3.6b2): once a minute the agent lists the host names of its Caddy's HTTPS routes (wildcards left out, at most 64) and, for each name not read in the last ten minutes, opens a TLS handshake to `127.0.0.1:443` with that name as SNI and reads the certificate presented, without sending a request. A certificate that does not name the host (Caddy's fallback while it has none) is not reported. A handshake that fails keeps the last reading, since Caddy's listener may be restarting; whatever the outcome, a host waits ten minutes before its next handshake. A reading not refreshed for thirty minutes, because Caddy's routes or listener stay unreadable, is no longer reported. Control characters, C0 and C1, are removed from the issuer. The state report carries the expiry and the issuer of each (`CertificateStatus`, issuer at most 64 bytes); a name no longer routed is dropped. The control plane ignores the whole list when any entry is invalid (more than 64, a malformed name, a missing expiry or one outside 2000 to 2200, an issuer over 64 bytes or with a control character). It keeps the names that are domains of the node's organization, compared without case or a trailing dot, in `domain_certificates`: one reading per domain and node, since each node's Caddy holds its own certificate. A new certificate (another expiry or issuer) is audited as `domain.certificate_observed`, by the node, with the previous expiry; an unchanged reading only refreshes `observed_at`, at most every five minutes. `GET …/applications/{applicationId}/domains` shows for each domain, among the readings received in the last hour, the one that expires first, or `null`. The hour is measured from `observed_at`, when the control plane stored the report, not from the agent's TLS read: since the agent reports a cached reading for up to thirty minutes after its last successful read, the reading shown can rest on a read up to about ninety minutes old.

Disk budgets (ADR 0022): once a minute the agent asks Docker for the writable-layer size (`SizeRw`) of every managed container. A running container whose size exceeds its `sk.disk_bytes` label is stopped with a 5-second grace period, after its intent is recorded as stopped (so the reconciler does not start it again) and its reason `disk_limit` is recorded. The state report carries that reason (`ContainerStatus.stop_reason`) until the container is removed. A label that is not a budget the agent writes (64 MiB to 1 TiB, canonical decimal) is ignored. The log names the container, its budget and its size, never a path.

State-report collection (M1.6b1) reads Docker's complete managed-container inventory, including stopped containers, every second. It emits on observed changes and every 30 seconds, starting again after each Welcome, with the session epoch and collection-start timestamp. Only canonical container IDs/names, runtime state and `sk.managed` are transmitted; arbitrary labels, environment, commands and health claims are excluded. A container Docker reports as `removing` counts as absent. An invalid inventory, Docker failure, more than 256 managed containers or a frame over 60 KiB suppresses the whole observation, never a partial snapshot; such failures are logged when they start and when they end. Collection runs separately from the single stream writer and stops with its session. The control plane (M1.6b2) rejects a report with a stale epoch on the stream. It ignores a whole report with any invalid container, and otherwise compares it with the placed allocations of the node named by the certificate: containers matching none of them are kept for the node in `unmatched_containers` (#501): replaced when the set changes, and audited then as `node.unmatched_containers_changed` (by the node, with the names added and gone and the count), a seen container now absent reads as `missing`, and a replica never seen stays unobserved because its container may not exist yet. Observations live in `allocation_observations`, apart from the scheduler's reservation in `allocations`. State changes are audited as `allocation.observed`, by the node; an unchanged state only refreshes `observed_at`, at most once a minute.

`HealthCheck` probes a managed container from the agent:

- **Target:** its private network address only, never loopback, link-local (for example cloud metadata) or public addresses. The port is the requested TCP port. For HTTP, it is the one TCP port the container's spec declared, which the agent records at creation (label `sk.probe_port`), because the image may expose others; failing that, the single exposed TCP port.
- **HTTP:** a `GET` that never follows redirects; 2xx and 3xx count as healthy. The path is absolute and not network-path, printable, at most 2048 bytes.
- **Timing:** interval 1 s–1 min, timeout no longer than the interval, start period up to 10 min, thresholds 1–10, overall deadline up to 30 min.

`RunReleaseTask` runs a validated container spec once, with the restart policy forced to `no`. It creates the container, then starts it, waits for it to exit within its timeout (1 s–1 h) and removes it, all in one non-retryable step, so the exit code is the final result. On timeout the task is killed and removed. After a crash it is compensated (removed), never run again.

Each container is labelled with its name and an `sk.spec` fingerprint of its spec, computed with secret values replaced by their versions. A replay reuses the same container; a different spec under the same name is refused.

The agent only adopts or changes resources that carry its `sk.managed=true` label; a same-named unmanaged network or volume is refused. Image pulls accept only digest-pinned references, plus optional credentials that are short-lived and scoped to the image's own registry (`docker.io` for a reference without a registry host, never the name of its namespace). The `sk.` label namespace is reserved for the agent.

### 3.6 Confirmation tokens

- Issued by the control plane (`POST /api/v1/organizations/{organizationId}/confirmations` with `action`, `target` and the typed `name`, 201) after the user types the resource name in the UI or passes `--confirm <name>` in the CLI. Any member may call it. A session needs Origin/CSRF; an API token needs `organization.read` to reach the route and the action's permission in its scopes. The command requires the action's live permission, answers 404 for unknown or hidden targets and 400 `confirmation_name_mismatch` for a wrong name. There is no encrypted retry: a lost response is answered with a new confirmation.
- Format: compact JWS signed with EdDSA (Ed25519) by the installation's confirmation key. Claims: `jti`, `org`, `action`, `target`, `iat`, `exp` (5 minutes), `sub` (user).
- The agent receives the public key at enrollment (`confirmation_public_key`), verifies the signature, the expiry, and that `action` and `target` match the request.
- Single use is enforced on both sides: the control plane marks the token used; the agent stores used `jti` values in SQLite until `exp`.
- Encoding: the header is exactly `{"alg":"EdDSA","typ":"JWT"}`. The payload is exactly `{"jti","org","action","target","sub","iat","exp"}` in that order: UUIDv7 `jti`, `org` and `sub`, `exp = iat + 300`, all base64url without padding. The signature is the raw 64-byte Ed25519 signature of `header.payload`. Verifiers reject any other header, extra or missing claims, non-canonical encodings and tokens over 2 KiB.
- Agent verification (`agent/internal/confirm`):
  - The agent uses the same strict parser and the public key from enrollment.
  - It requires `org` to be its own organization, the action and target to match the request, `iat` at most 60 s ahead and the token unexpired.
  - It records the `jti` in its journal until `exp`.
  - A test vector signed by Node.js checks that the TypeScript and Go implementations agree.
  - `RemoveVolume` needs a token with action `volume.remove` and the volume name as target. The token is spent in a non-retryable first step; the volume is then removed only if it carries `sk.managed=true`. The control plane will issue `volume.remove` confirmations once volumes are resources (M5).
- Actions come from a closed catalog (`modules/confirmations/domain/confirmation-token.ts`), each with the permission its requester needs and the level it is checked on:
  - `node.remove`: `node.manage` on the organization, target = node id.
  - `node.container.remove`: `node.manage` on the organization, target = `<node id>/<container name>`, name = the container name. Only an untracked container (#501) resolves. The control plane checks it alone: the removal it asks for keeps the container's volumes, which needs no token on the agent.
  - `application.delete`: `environment.update` on the environment the application lives in, target = application id. The control plane reads the application first to learn where it lives; an unknown application and one the requester may not administer both answer 404.
- Issuance requires the live permission and the resource's exact current name, typed by the user. The control plane stores only the token id, binding, expiry and use time (`confirmation_tokens`, tenant RLS, no DELETE grant), and audits `confirmation.issued`. A destructive command consumes the token inside its own tenant transaction, through one conditional update, so the token is spent only if the command commits.

### 3.4 Operation journal

- Local SQLite table `operations(action_id PK, idempotency_key UNIQUE, kind, payload_hash, state, step, completed, attempts, revision, result_json, started_at, updated_at, last_error)`. SQLite uses WAL and FULL synchronous writes in a private state directory. An exclusive process lock prevents two agents from executing against the same journal. The database file is 0600 and symlinks are rejected.
- Checkpoints use revision compare-and-swap and append an `operation_history` row in the same transaction. Payloads are never stored: only SHA-256 hashes and bounded metadata. Results contain resource ID, image digest and exit code; arbitrary output and raw errors are excluded. Replaying an idempotency key with a different action kind or payload hash fails.
- States: `pending`, `running`, `succeeded`, `failed`, `cancelled`, `compensating`, `compensated`.
- The agent writes `pending` before doing anything, updates `step` after each side effect, and sends `ActionUpdate` on every transition.
- On restart, `running` operations are resumed from `step` if the action is idempotent at that step, otherwise compensated (for example: a half-created container is removed). The executor records the current step before invoking it and advances `completed` only afterwards. Every step declares retry safety and an idempotent compensator; an uncertain non-idempotent step and all preceding steps are compensated in reverse order. Compensation itself is checkpointed and safely retryable. Shutdown leaves recoverable intent instead of converting it to success.
- Journal checkpoints are written even after shutdown is signalled, so a completed side effect is never mistaken for an uncertain one. If announcing a step start fails, the step marker is cleared before returning because the step never ran. A compensator that still fails after five attempts moves the operation to `failed` (terminal, `last_error` recorded) for operator attention instead of retrying on every boot.
- Execution plans are registered code with a version and at most 64 unique step names, never remote code. The intent hash binds the payload hash to the plan version, ordered names and retry policy. The caller reconstructs inputs from desired state or request replay; raw payloads are never journaled. A per-store executor gate prevents concurrent duplicate side effects. The gate is per lane (ADR 0032): builds have their own, so a server runs at most one build and, beside it, its other actions one at a time; a build touches only BuildKit and the registry. Committed transitions are offered to an ActionUpdate callback; delivery failure pauses further effects, and retry republishes the latest durable state. Concrete Docker/Caddy handlers and stream dispatch are wired in their own milestones.
- Idempotency: the same `idempotency_key` returns the stored result without re-executing.
- Dispatch (`agent/internal/actions`) rejects malformed requests before journaling anything, and answers each with a single `FAILED` update carrying a fixed, redacted message. Rejected requests include:
  - an action id that is not a UUIDv7, or an idempotency key outside `[A-Za-z0-9._:-]{1,128}`;
  - a missing or unregistered action kind;
  - a lease epoch other than the node's;
  - a missing deadline;
  - a handler validation error.
- A step that fails says why with a fixed text from a closed list, or `action failed` (issue #265). Nothing else about the failure leaves the server.
  - The Docker client reads the daemon's message about a failed pull, names a cause and drops the message, which can hold hosts, paths, tokens or credentials.
  - The journal keeps the cause as a short code (`last_error`), through compensation, a replay and a restart. A cause that is not a code is dropped.
  - The dispatcher sends the text of a cause it lists:

The control plane records the final state of an expired action, as a terminal event of its own; a refusal keeps it expired. Either ends its recovery.

### 3.5 Local state

- `desired(resource_id, spec_json, version)`, `actual(resource_id, status_json, observed_at)`, `routing(version, table_json)`, `lease(epoch, expires_at)`, `used_confirmations(jti, expires_at)`.
- `spec_json` stores secret references (name and version), never secret values. Typed protobuf snapshots are cloned and every `debug_redact` field is cleared recursively before JSON serialization; caller-owned execution data is unchanged. Unknown protobuf fields are removed and snapshots are capped at 1 MiB. See section 9 for how secrets reach containers.
- Desired and routing versions cannot move backwards; same-version replays must have identical canonical JSON. Actual observations cannot regress in time. Lease epochs cannot regress, and a same-epoch expiry cannot shorten. Confirmation IDs are consumed transactionally once until their verified expiry (at most five minutes); signature and scope validation belongs to the confirmation handler.
- The agent reconciles its own containers against `desired` every 30 s, restarting crashed managed containers within their restart policy, even without control plane contact.

## 4. Data model

PostgreSQL. Application tables live in the `public` schema; pg-boss owns `shipkeep_jobs`. All tables have `id uuid` (UUIDv7), `created_at`, `updated_at`. Tenant-scoped tables carry `organization_id` and every query filters on it, enforced twice:

- In repositories, which always take the organization id from the request context.
- By PostgreSQL row-level security. The API connects with a role that has RLS enforced. Tenant operations run through `PrismaUnitOfWork.runTenant`, which binds `SELECT set_config('app.org_id', $1, true)` to the same transaction as repository and audit writes. Policies compare the organization id with that transaction-local setting. Cross-tenant jobs (scheduler, reconciler) use a separate role and are reviewed as security-sensitive code.

Tenant relationships use composite foreign keys carrying the organization id; role bindings also include the environment's parent project, preventing cross-tenant and sibling-project references even through direct SQL. Each membership has one binding per project/environment scope, including the null environment used for a project-wide role. Memberships must be removed explicitly before deleting a user. Organization slugs are globally unique; project slugs are unique per organization; environment names are unique per project. Slugs and environment names use 1–40 lowercase ASCII letters, digits and hyphens, starting with a letter; display names contain 1–80 characters. New projects default to pull-request configuration writes, and environments default to protected with no automatic failover.

Organization, membership, project, environment, role-binding, node, node-certificate and join-token tables enforce RLS for reads and writes, including table-owner queries. Missing or cleared transaction context denies access. Before each tenant operation, the unit of work verifies both login and effective roles, their role memberships, all five forced-RLS tables and the `row_security` setting. It rejects superuser, `BYPASSRLS`, role-administration or replication capabilities, tenant-table ownership, tenant `TRUNCATE`/`TRIGGER` grants and `CREATE` on the public schema. Tenant repositories and route wiring follow in M2.3c2b/M2.3d before HTTP exposure. PostgreSQL superusers and `BYPASSRLS` roles still bypass forced policies, so integration tests use a separate restricted login. See [PostgreSQL row security](https://www.postgresql.org/docs/17/ddl-rowsecurity.html).

Fleet operations follow ADR 0015. The agent gateway checks certificates and renews them under `runTenant`, using the organization from the TLS-verified certificate's SPIFFE ID. Enrollment first calls `runEnrollment(tokenHash)`: it sets a transaction-local `app.join_token_hash` with no tenant or account context, so the SELECT-only `join_token_lookup` policy exposes only the join token with that SHA-256 hash. The node, its certificate, the token consumption and the audit event are then written under `runTenant` for the token's organization.

Organization administrators (`node.manage`) manage the fleet over session-only routes. `POST /organizations/{organizationId}/join-tokens` (201) requires Origin/CSRF, the password and the configured second factor. It returns the single-use token, its expiry and the installation CA fingerprint once, and it has no encrypted retry: a lost response is answered with a new token. `GET /organizations/{organizationId}/nodes` returns the organization's nodes (status, labels, sanitized facts, lease epoch, last heartbeat) with `cursor`/`limit`. `GET /organizations/{organizationId}/nodes/{nodeId}` returns one of them, removed ones included, and `GET /organizations/{organizationId}/nodes/{nodeId}/replicas` the replicas placed on it (at most 200, by application name, `truncated` when there are more): each with its application, project and environment, the CPU and memory reserved for it, and what the agent last saw, as for an application's replicas. Both answer 404 for a node outside the organization. `GET /organizations/{organizationId}/nodes/{nodeId}/untracked-containers` lists the node's untracked containers (#501): those of its unmatched containers whose name, as the pipeline builds it, ends with the last 12 characters of exactly one application of the organization, none of whose deployments is underway (a deployment underway may still run its release task or drain its previous replicas). Each comes with its application, project, environment, release and replica as its name says, its state and since when it is unmatched. `POST /organizations/{organizationId}/nodes/{nodeId}/untracked-containers/{name}/remove` (202, session only) asks the agent to remove one of them, without its volumes. It needs `node.manage` and a confirmation token for `node.container.remove` on that container; a container that is not untracked any more answers 409 before the token is spent. The token is spent in the same tenant transaction that queues `RemoveContainer` (key `u:<confirmation id>:remove`, one hour) and audits `node.untracked_container_removal_requested` with the container, its application and release, the confirmation and the action. `POST /organizations/{organizationId}/nodes/{nodeId}/remove` (204) removes a node. It needs `node.manage` (a session, or a scoped token) and a `confirmation` token for `node.remove` on exactly that node, issued to the same account. The token is spent in the same tenant transaction that marks the node `removed`, revokes all its certificates and audits `fleet.node.removed` with the confirmation id. The node's gateway stream closes at its next credential check. Removing it again answers 404.

`POST /organizations/{organizationId}/nodes/{nodeId}/public-addresses` (200, `node.manage`, a session or a scoped token) replaces the public addresses an administrator declares for a node and returns the node (PLAN M3.6b1). The domain check compares DNS answers with them.

- The body is `{publicAddresses}`: at most 8 values; an empty list clears them.
- Each value must be a bare IPv4 or IPv6 address that the control plane's SSRF list considers globally routable. Hostnames, zone ids, ports, prefixes, surrounding whitespace and IPv4 written inside IPv6 (`::ffff:a.b.c.d`) are refused with 400 and the position of the first bad value, never its text: `node_public_address_invalid`, `node_public_address_not_public`, `node_public_address_ipv4_embedded` or `node_public_addresses_too_many`.
- Values are stored canonical (RFC 5952 for IPv6) and deduplicated, in the given order. The database bounds the list too.
- A change is audited as `fleet.node.public_addresses_changed` with the new and previous lists; saving the same list records nothing. The write is a compare-and-swap on the list just read: a concurrent change answers 409 `node_public_addresses_changed`. A removed node answers 404.
- Addresses are declared, not observed: the gateway's view of an agent connection can be a NAT, proxy or private address (see section 16).

Agent upgrades roll out to one server at a time (ADR 0028, section 2). Both routes need `node.manage`.

- `GET /organizations/{organizationId}/agent-upgrades` (200) gives:
  - `version`, the control plane's own (`SHIPKEEP_VERSION`), which agents are upgraded to; null on a development build;
  - `pending`, the servers whose agent runs an older release on `amd64` or `arm64`. A `dev` agent is never listed;
  - `rollout`, the newest rollout, running or ended, with its servers in turn order, its `position` and its `failure`.
- `POST /organizations/{organizationId}/agent-upgrades` (202, a session or a scoped token) starts a rollout. The body is `{version}`, the version the overview gave.
  - It answers 409 for:
    - a development build (`agent_upgrade_unavailable`);
    - a control plane that runs another version by now (`agent_upgrade_version_changed`);
    - a rollout already running (`agent_upgrade_running`, also kept by a partial unique index);
    - no server to upgrade (`agent_upgrade_not_needed`);
    - more than 1,000 servers (`agent_upgrade_too_many`);
    - a release whose digest or Sigstore bundle cannot be read (`agent_release_unavailable`).
  - Before anything starts, after the access check and outside any transaction, it reads that digest and bundle for each architecture. They come from the release's `checksums.txt` and `<archive>.sigstore.json`, over HTTPS, from GitHub's release hosts only, redirects included, at most 64 KiB each. The control plane relays them and trusts neither: the agent checks both (SPEC 3.3).
- A pg-boss queue runs the rollout. Each server's turn:
  - **Skip.** A server that is removed, already on the version or later, `dev`, or on another architecture is skipped.
  - **Wait first.** The turn waits while the server is not connected, failing after 5 minutes (`node_unavailable`). It also waits while the server has any other unfinished action, which is how a deployment touching it shows, failing after 30 minutes (`node_busy`).
  - **Send.** It then sends `UpgradeAgent` with the key `au:<rollout>:<node>` and a 30-minute deadline. Every action admission locks its node's row, and an upgrade is admitted only when no other action of the node is unfinished (`node_busy`), so a deployment action admitted meanwhile makes the turn wait instead.
  - **Stop.** An action that does not succeed stops the rollout (`action_failed`, with the action's reason). So does a server that never comes back (`not_confirmed`).
  - **After success.** The turn ends when the server reports the new version in a hello. A heartbeat recorded 150 seconds or more after the success, still on the previous version, reads as a rollback by the upgrade guard (`rolled_back`). No new version within 25 minutes reads as `not_confirmed`.
  - **Wake-ups.** A finished action, a reported version or a server coming back wakes the rollout at once; otherwise it looks again every 15 seconds. A run that fails is queued again after 60 seconds rather than left to the queue's retries, and the overview queues a running rollout again, so a running rollout never stays without a run.
  - **Audit.** The rollout records `fleet.agent_upgrade.started` (with the actor), `fleet.agent_upgrade.node_upgraded` or `node_skipped` per server, then `fleet.agent_upgrade.succeeded` or `failed` (with the server, the reason and the action's reason). The actions themselves are audited as `fleet.action.*`.
- Rollouts are kept as their history: the runtime role cannot delete them.

Audit events are under forced row security too. In a tenant transaction the runtime role reads only that organization's events. It never reads account or system events (`organization_id` null). Appends stay allowed from every command transaction, but a tenant context can only append events of its own organization or of none. No UPDATE or DELETE policy exists. Audit inserts do not read the row back. Reading system events requires an installation-administrator capability that does not exist yet (see section 16).

Organization owners and admins (`audit.read`) read their audit log with `GET /organizations/{organizationId}/audit-events`. It is newest first, with a `cursor` and `limit` (1–100), and optional exact `action`, `targetType`, `targetId` and `actorId` filters plus a `from` (inclusive) and `to` (exclusive) period. `GET .../audit-events/export` returns the same filters as JSON Lines, at most 10,000 events, with `X-Shipkeep-Truncated: true` when older matches remain. Both routes accept a session or a scoped API token with `audit.read`. Reads run in the organization's row security context and are not themselves audited.

Tenant identifiers must be canonical UUIDv7 values. Nested operations can join only the same organization; overlapping sibling scopes within a shared outer transaction are rejected before they can race on connection settings. Context is cleared before returning to an outer identity command and is transaction-local across commit or rollback. Setting a tenant context is not permission to access it: application authorization must still verify current membership and resource ancestry. Storage diagnostics are replaced by an opaque service-unavailable response.

Before choosing an organization, `runAccountDiscovery` sets a transaction-local `app.user_id` from the authenticated account and clears `app.org_id`. SELECT-only policies expose that active, verified account's own memberships and their organization metadata. They expose no other members, project/environment contents or role bindings, and grant no tenant writes. Account discovery and tenant scopes cannot nest into each other or change identity while active; both settings are cleared on exit. An arbitrary account identifier from request input must never be used as the discovery identity.

Every session the API opens (Prisma and the job queue) runs in UTC: each new connection of their pools runs `SET TIME ZONE 'UTC'` before anything else, which holds against a server, database or role default and against a login trigger, and both refuse to start when `current_setting('TimeZone')` is not `UTC` (#322). `DATABASE_URL` is used as written. A pooler that shares server sessions between clients (transaction pooling) is not supported. On an installation whose database already ran in another zone, timestamps written before this rule stay shifted by that offset: short-lived ones (sessions, rate-limit windows, codes) expire on their own, audit and deployment times do not change. `node main.js account reset-password` ends every session and token of an account. The driver sends a `Date` as text without an offset, which PostgreSQL reads in the session zone; in another zone, instants the API writes and instants PostgreSQL computes (`now()`) would disagree by the offset. The migration connection is configured separately with `MIGRATION_DATABASE_URL`; the API reads only its restricted `DATABASE_URL`. Provisioning grants explicit DML on runtime tables and only SELECT/INSERT on audit events, excluding migration tracking and future tables by default. Migrations create the queue schema; pg-boss manages objects only within `shipkeep_jobs` and does not require database-wide schema creation. Upgrade provisioning preserves existing queue objects/jobs while transferring their ownership inside that schema. See [database-role setup](DATABASE_ROLES.md) for development and deployment procedures.

Fleet nodes and enrollment tokens reference an existing organization. Their foreign keys restrict organization deletion instead of cascading into servers, certificates or enrollment history. The fleet migration aborts if legacy rows reference missing organizations; an operator must reconcile these records with their verified owners before retrying the upgrade. It never creates a default owner, reassigns a server or deletes an orphan. Fleet enrollment authorization and transaction boundaries are maintained separately in the M1.2 stack; these foreign keys alone do not grant access or enforce fleet RLS.

Membership writes serialize on the organization through a no-op row update, producing a new row version that also prevents write skew under repeatable-read snapshots. Deferred constraint triggers require at least one owner at commit, allowing atomic creation and ownership transfer. The trigger temporarily selects each affected tenant from stored row identifiers and restores the prior transaction context, so changing context before commit cannot hide the affected organization from the check. It runs with invoker privileges and a fixed search path. Existing ownerless organizations abort migration rather than receiving an invented owner. Deleting the organization permits its membership cascade; user deletion remains restricted while memberships exist.

## 5. State machines

### 5.1 Deployment

```text
queued -> building -> built -> releasing -> scheduling -> starting -> health_checking -> switching -> draining -> succeeded
any state -> failed      (previous release keeps serving)
any state -> cancelled   (user cancel; same guarantee)
succeeded -> rolled_back (when a later rollback targets the previous release)
```

- `releasing` is skipped when no release command is defined.
- A stop is a deployment whose plan has `stop`: `queued -> draining -> succeeded`. It starts nothing, resolves no image and places nothing, so it works when the registry is unreachable or the nodes are full.
  - `draining` removes the application's route on every node that served, then stops and removes every placed replica of the application, whatever its release.
  - Success marks those allocations stopped, which frees what they reserved (section 6). The application, its releases and its history stay.
  - A failed stop leaves the replicas it could not remove placed, with their reservation, and can be asked again.
  - After a stop nothing serves: any deployment that succeeded can be rolled back to, and deploying starts the application again.
- Entering or leaving maintenance (ADR 0025) is a deployment of the release that runs, whose plan has `maintenance` (`enter` or `leave`): `queued -> switching -> succeeded`. It starts, stops and places nothing, and needs no image.
  - `switching` sends `UpsertRoute` to every node that hosts a placed replica of the application, with its domains: entering sends the maintenance page (`maintenance`, no upstream) once the requests the replicas serve have drained; leaving sends the replicas again, with nothing to drain.
  - Every replica keeps running and keeps its reservation, whether the change succeeds or fails.
  - A failure or a cancellation during `switching` puts back what the routes served: the replicas when entering, the page when leaving.
  - The application is in maintenance when its last succeeded deployment entered it. A stop that succeeds afterwards ends it.
- A failure before `switching` never changes routing.
- A failure during `switching` restores the previous route atomically: the previous release's replicas, with the hostnames that release declared, not those of the failed one (issue #485). A node the switch routed where nothing was routed before loses that route. The hostnames come from the newest release among the previous replicas, which never changes, so a restarted worker builds the same restoration.
- The aggregate is `packages/domain/src/lib/deployment.ts`. A deployment's plan, fixed when it is queued, records whether it builds (image sources skip `building` and `built`) and whether it runs a release command. Stopping it as failed or cancelled reports whether traffic is untouched (before `switching`), must be restored (during it) or already on the new release (`draining`). Failure reasons are stored bounded to 512 characters, without control characters.

- The pipeline planner (`apps/api/src/modules/deployments/domain/pipeline.ts`, PLAN M3.4c3b) is a pure function from what was observed to what comes next. The worker (M3.4c4) applies its decision and calls it again whenever an agent action finishes, so every stage resumes after a restart. A run that throws is queued again after 15 s, doubling up to 5 min, instead of through pg-boss retries, which end; at start and every 5 minutes, the worker also queues again each deployment whose latest run failed for good. A deployment never waits for a wake that nothing would send (issue #486). Its inputs are the deployment, the release, the placed replicas, the replicas of the serving release and the outcomes of earlier actions. Its decision is one of: resolve the image, place N replicas, enqueue actions (idempotency key `d:<deployment>:<step>`), advance, fail, or done.
  - `queued` resolves the image digest.
  - `releasing` places the replicas, then ensures the environment network, pulls the image and runs the release task on the first replica's node.
  - `scheduling` places the replicas if that was not already done.
  - `building` (ADR 0030), for a Git application with `build.type` `dockerfile`, `railpack` or `nixpacks`: the replicas are placed first, and the server of the first one builds with `BuildImage` (key `d:<deployment>:build`), at the release's commit, its context and Dockerfile read as the agent reads paths (`./api/` is `api`, `.` the root, `Dockerfile` by default; Railpack and Nixpacks take none). It fetches `https://github.com/<repository>.git` with a token of the organization's GitHub App, minted outside any transaction, that reads that repository's contents only. Once the build action has ended (succeeded, failed, cancelled or expired), the next run of the deployment asks GitHub to revoke the token, outside any transaction, then clears it from the stored action and audits `deployment.build_token_revoked` (`ended`: `github`) in one transaction: never while BuildKit may still fetch, and once, since a later run finds it cleared. When GitHub cannot be asked, the token stays in the action and the run answers `wait`, so the deployment's job comes back and asks again, across restarts; 70 minutes after the build was queued the token has expired by itself, and it is cleared without GitHub (`ended`: `expiry`). A token minted for a build that this run did not queue (the deployment moved on, a step could not be prepared, or another run queued the build first) is revoked at once. It pushes the release's image, `<control plane host>/<organization>/<application>:<release number>`, with a registry grant that pushes, valid until the action's deadline. The digest it answers becomes the release's, audited as `release.image_built` (`digest`, `commitSha`). A failed build says why: its output, its time limit, or a server without a builder (`--migrate yes`). GitHub out of reach makes the run wait and try again.
  - Every pull of an image of the installation's registry carries a grant that only pulls, issued when the pull is enqueued and valid until its deadline; other registries' credentials are those the organization stored (ADR 0019).
  - `built` moves on at once.
  - `starting` ensures the network, pulls, creates and starts each replica.
  - `health_checking` probes `run.healthcheck` on each replica (deadline: the start period plus 2 min, at most 30 min).
  - `switching` upserts the application route (id = application id) on each node with that node's replicas as container upstreams (ADR 0017), but only when `domains` is set.
  - `draining` removes the route from nodes no longer serving, then stops the previous replicas and removes their containers, without their volumes.
  - Any action ending in failed, cancelled, expired or compensated fails the deployment, as do a non-zero release exit, an unhealthy replica or a missing container id.
  - A release that the planner or the scheduler cannot read, for example a stored value that is out of range, also fails the deployment, with that reason. The run does not throw: a thrown run is only retried, and the deployment would keep the application's single active deployment.
  - `recovery` then:
    - force-removes the new replicas that were created, which never served traffic;
    - if the switch was interrupted, restores the previous upstreams and removes the route from nodes that only hosted new replicas;
    - does nothing once draining began, because the new release already serves.
  - The worker (`DeploymentPipeline`, run from the pg-boss queue `deployment-run`):
    - The `stately` policy keeps at most one queued and one active run per deployment.
    - Deploying and cancelling send a run in the command's transaction. Every final agent action whose key belongs to a deployment wakes it, and a run that waits on agents is checked again after 15 s.
    - A run applies decisions until the deployment waits or finishes. The image is resolved outside any transaction. Placement uses `placeReplicas` over the nodes as they are observed, and fails with each node's rejection reason when a replica does not fit.
    - Steps are enqueued with the system actor and a one-hour deadline. Transitions compare-and-swap the state, so concurrent runs cannot both apply.
    - Audit events: `release.image_resolved`, `deployment.placed`, `deployment.advanced` (`from`, `to`) and `deployment.failed` (`reason`, `routing`).
    - Success stops the replaced replicas. Failure and cancellation run `recovery` and stop the deployment's own replicas.
    - The worker starts with the agent gateway in `main.ts`.
  - Steps become proto actions in `deployments/infrastructure/agent-steps.ts`. Secret values are injected there at enqueue time, so they travel only inside the encrypted action payload. A full pipeline run is kept as golden vectors (`agent/internal/actions/testdata/control-plane-actions.txt`), and a Go test plans each one with the agent's own handlers, so the planner and the agent validators cannot drift apart.
  - Containers are named `sk-<name[0:24]>-<application id suffix>-r<release>-<replica|task>`, on the network `sk-env-<environment id>`. They carry the labels `shipkeep.application`, `shipkeep.release` and `shipkeep.deployment`; secrets are listed by name, and the worker injects their values.

### 5.2 Node

```text
enrolling -> ready -> suspect -> down -> ready (re-joined with epoch check)
ready -> draining -> ready | removed
```

- `suspect` after 15 s without heartbeat, `down` at lease expiry (60 s default).
- Until leases persist these transitions (M4.5), the control plane records a connected agent's hello and then its heartbeats at most every 10 s. That makes an `enrolling`, `suspect` or `down` node `ready`, audited once per transition as `fleet.node.ready`; `draining` and `removed` nodes keep their status. The hello also names the agent's version. When it differs from the node's stored `agent_version` fact, the control plane stores it and audits `fleet.node.agent_version_changed` with the previous and the new version: this is how it sees an upgrade, or its rollback (ADR 0028). A version that is not a release version or `dev` (`^[0-9A-Za-z][0-9A-Za-z.+-]{0,63}$`) is not stored. The API and the scheduler read a stored `ready` node as `suspect` 15 s and `down` 60 s after its last recorded heartbeat.
- `draining`: no new allocations; stateless allocations moved; requires Admin.
- `removed`: certificate revoked, allocations must be zero or confirmed for deletion.

### 5.3 Allocation

```text
pending -> pulling -> created -> starting -> healthy -> stopping -> stopped
starting -> unhealthy -> (restart within policy) -> starting | failed
```

## 6. Scheduling

1. Filter nodes: never a machine whose agent reports the role `control-plane-only` (ADR 0028), status `ready`, required labels, architecture matches the image, free CPU and memory reservations, free disk for the disk budget, required ports free, volume affinity for stateful workloads.
2. Rank: prefer nodes without another replica of the same app (spread), then lowest reserved memory ratio, then lowest reserved CPU ratio, then node name for determinism.
3. Stateful workloads are pinned to the node that holds their volume.
4. Scheduling is deterministic given the same inputs (unit-testable without a cluster).

The algorithm is `placeReplica` and `placeReplicas` in `packages/domain/src/lib/scheduler.ts`.

- A stateful workload is pinned only when some node already stores its volume; otherwise it is placed like any other replica and its volume is created there.
- Resource ratios compare exactly (integer cross-multiplication), never as rounded floats.
- `placeReplicas` places replicas one after another, each seeing the reservations, ports and spread of the previous ones, and reports how many did not fit.
- Disk (ADR 0022) is a check, not a reservation: a replica fits a node only if the free disk its agent last reported (`disk_free_bytes`) minus the disk budgets this placement already put there leaves the replica's budget plus 2 GiB (`DISK_MARGIN_BYTES`). A node that reported no free disk is not checked.
- An unplaced replica returns one rejection reason per node: `not_ready`, `architecture`, `labels`, `not_allowed`, `volume`, `cpu`, `memory`, `surge`, `disk` or `ports`, checked in that order, for operator explanations.
- A node whose agent reported no architecture, CPU count or memory has no capacity. It is rejected with `architecture`, `cpu` or `memory`, even for a replica that reserves nothing, and the other nodes are still considered.
- A replica reserves the CPU and memory limits its container runs under: `resources`, or the defaults of section 2.2. `resourceLimits` (`apps/api/src/modules/deployments/domain/container-plan.ts`) gives the placement request, the `Allocation` and the container spec the same two values. A node's capacity is its CPU count and its memory as its agent reports them, minus the control plane reservation it reports (`reserved_cpu_millis`, `reserved_memory_bytes`, ADR 0021; zero except on the machine that hosts the control plane), and placement never lets the reservations on a node exceed it.
- Placements of one organization run one at a time. `place` takes a transaction-level PostgreSQL advisory lock for the organization (`PipelineStore.lockPlacement`) before it reads the nodes and their load, and holds it until its replicas are stored or the transaction rolls back. Two deployments placed at the same moment therefore cannot both count the same room as free: the second one reads the load with the first one's replicas in it. It also reads the time once it holds the lock, so a node whose heartbeats stopped while it waited is not counted as ready.
- A deployment does not count the replicas it replaces (`nodeLoads`): they stop when it succeeds, and its own replicas are removed when it fails, so one of the two releases keeps the reservation. Without this, an application that fills its node could never deploy its next release. The load and the replaced replicas come from one query, so a replica stopped in between cannot free its room twice. Both releases run from `starting` to `draining`: for that time the limits on a node can exceed its capacity by those of the replaced replicas. A node that reports a control plane reservation is the exception (ADR 0021): there the replaced replicas keep counting until the deployment ends (`surge`), and a new release that does not fit beside them is refused with `surge` before anything starts, so that the overlap never takes the room of PostgreSQL and the API.

API tokens carry explicit scopes that can only narrow the owner's permissions.

Settings use explicit `organization.update`, `project.update` and `environment.update` permissions at their corresponding resource scope; a resource administrator cannot change organization settings. Display names are trimmed and limited to 1–80 Unicode code points without control, format or unpaired-surrogate characters. Slugs and environment names are canonical lowercase ASCII identifiers without whitespace, including trailing newlines. Project/environment configuration values are closed enums; protection is a boolean with no string/number coercion. New projects use pull-request writes and new environments are protected with no automatic failover unless explicitly configured otherwise.

The shared tenant policy is default-deny for unknown permissions, roles and invalid resource hierarchies. Resource ancestry, membership and environment protection must be loaded from current database records by the authorization adapter. Account-only `profile.read` remains outside tenant RBAC. Organization members may read organization metadata; a resource binding permits parent-project navigation but does not grant access to sibling environments. An explicit environment binding replaces the inherited project role for that environment, including when it reduces access. Missing protection metadata denies deploy, secret-write and container-exec decisions even for administrators. Ambiguous duplicate effective bindings are denied.

`TenantAccess` resolves the current active/verified membership, project ancestry, environment protection and role bindings inside the caller's tenant transaction before evaluating that policy. Every resource query includes its organization, and environment queries include their parent project. Caller-supplied role or protection fields are ignored. Changed roles, protection and account status take effect on the next decision; no permission cache is used. Missing resources and denied permissions use the same resource-not-found response. The read-side module is independent of identity commands; session/bearer route wiring follows in M2.3d, with role mutations serialized against identity locks in M2.3c4.

An explicit environment role replaces the member's project role for that environment instead of adding to it, so a narrower environment binding can restrict access. Only an actor with project-level member management may create or remove an environment override for a member who administers the project, so an environment-only administrator cannot restrict a project administrator.

Organization admins may manage non-owner memberships, but only owners may grant or remove ownership. Removing or demoting the last owner is forbidden. An owner hands ownership to another admin with `POST /organizations/{organizationId}/members/{membershipId}/transfer-ownership` (issue #255), under the same fresh password and second factor as any membership change: in one transaction the admin becomes an owner and the caller an admin, each change audited as `membership.role_changed`; the new owner's credentials are invalidated and the caller's session rotates. A target that is not an admin, including the caller, answers `409 ownership_target_not_admin`; a caller who is not an owner, `404`. Commands must lock the organization before reading the owner count and changing membership; the pure policy alone provides no concurrency guarantee. Project/environment administrators may only manage bindings within their authorized scope, never organization membership or ownership. Destructive-action authorization remains separate from the single-use confirmation required by M2.5.

Organization membership commands add existing active verified accounts by email; invitations to unknown/unverified accounts are not implemented. They recheck the directory candidate's email and state under ordered account locks, then lock the organization and repeat live member-management authorization. Existing memberships require an explicit role change when the requested role differs. Same-role requests are idempotent; removal cascades resource bindings. Only owners may manage owners, and simultaneous owner departures cannot remove the final owner (`last_organization_owner`). Disabled accounts may be removed but cannot receive a new membership/role. Membership writes, their audits and affected-account credential invalidation commit together.

Resource role assignment resolves an exact existing organization member by email only after the actor is authorized to manage that project/environment. It cannot add organization membership or grant organization ownership. New/changed bindings require an active verified account with the organization `member` role; existing bindings can still be removed after promotion or disabling. Project administrators manage their project and authorized environments; environment-only administrators manage only that environment. Explicit environment downgrades also constrain role administration, so a downgraded member cannot remove their own restriction. Removing an override may restore an inherited role and therefore invalidates credentials just like an assignment. Same-role or already-absent binding requests preserve credential versions while auditing proof confirmation.

Directory lookups never answer before the actor's password is checked: an unknown address and a wrong password give the same authentication failure, so membership and role commands cannot be used to discover which accounts exist or belong to an organization. An administrator of a single environment may not create or remove an environment override for a member who administers the whole project; only a project-level administrator (or an organization owner/admin) can, because the project admin could otherwise not undo the restriction.

The organization membership directory requires organization-level member management. Resource administrators can list authority only for their authorized project/environment: organization owners/admins plus members with applicable grants, including disabled members for cleanup. Each row separates the effective resource role/source (`organization`, `project` or `environment`), direct binding and inherited project binding. Membership metadata includes email and active state but no credentials. One SQL snapshot resolves bindings before pagination, preventing inconsistent parent/override reads during concurrent grant changes. These administration lists share the catalog's bounded exclusive UUID pagination.

Resource commands use the public `AccountMutationAuthority` identity boundary to recheck the active verified account and security version under its mutation lock. Operations that grant/change roles can require password and configured MFA proof; proof consumption, resource writes, audit and session rotation share the caller's transaction. Rotation through this boundary is available only within the same reauthenticated callback and for its account/version. A password reset racing password verification invalidates the mutation before it runs. Transport authentication supplies the actor context; request-body account ids are never trusted as the caller.

Privilege changes acquire the actor and affected account locks in canonical UUID order before any organization lock. Commands must not enter that boundary with an actor lock already held; preliminary resource authorization/directory lookup is read-only and repeated under the ordered locks. Fresh password/MFA proof is required. A changed role increments the affected account's security version, invalidating its sessions and API tokens atomically with the role/audit writes. Self-changes return a rotated session; changes to another account preserve the administrator's session. Idempotent no-ops do not rotate credentials but audit confirmation because a configured MFA proof may have been consumed. Proof expires when its callback ends, including for inherited detached asynchronous work. The internal verified-account directory returns only account id/email/active status and is available to authorized membership commands, never as an unauthenticated search endpoint.

Creating an organization requires fresh password and configured MFA proof. The organization, initial owner membership, ownership audit and security-version/session rotation commit atomically. The caller receives the new session; existing sessions and version-bound API tokens lose authority. Organization settings changes require live owner/admin authority under the caller's account lock. Globally occupied slugs return only `organization_slug_unavailable`, including concurrent creation/rename conflicts; tenant metadata and database diagnostics are never returned. Resource deletion is not exposed by these commands.

Project and environment creation/settings commands recheck live scope permissions under the account lock and commit their settings and audit together. Project slugs are unique per organization; environment names are unique per project. Collisions return fixed `project_name_unavailable` or `environment_name_unavailable` errors. Settings updates replace the supported settings as a whole; creation and replacement use the same validated defaults. Organization/project ownership comes only from the authorized resource path and cannot be changed through settings. Environment-only administrators cannot change their parent project or create sibling environments.

Resource catalogs require the current verified account/security version. Organization discovery uses the account-scoped SELECT policies; project and environment catalogs use tenant scope and apply live membership/binding filters in SQL before pagination. Owners/admins see their organization's resources; other members see only granted projects/environments, including parent navigation for environment-only grants. Lists use descending UUID order, an exclusive cursor and 1–100 items (100 by default); a full terminal page may return a cursor followed by an empty page. Cursors are range bounds, never cross-tenant existence lookups. Detail queries use the same live ancestry/permission checks and uniform missing-resource response.

Administration directories use session-only `GET /organizations/{organizationId}/members` and nested project/environment `/bindings` paths. Each requires `member.manage` at its exact scope; bearer credentials are rejected. Responses contain public membership metadata and, for bindings, effective/direct/inherited roles. The shared exclusive UUID pagination is validated at the HTTP boundary; filters are applied before pagination. Disabled members remain visible for authorized cleanup.

Membership writes are session-only and require Origin/CSRF, the current password and the configured second factor; bearer credentials are rejected even with `member.manage`. `POST /organizations/{organizationId}/members` (201) adds an existing active verified account by email with an organization role. `POST /organizations/{organizationId}/members/{membershipId}/role` (200) changes the role, and `POST .../members/{membershipId}/remove` (200) removes the membership and its resource bindings. Each answers `{ membership, session? }`, where `membership` is null after removal. `session` appears only when the caller changed their own role; the rotated credentials are then set only in cookies. Changing another account advances that account's security version, ending its sessions and tokens. An unknown address with a correct password answers 404, like a hidden resource. Encrypted retries cover these three routes, and every replay rechecks live `member.manage`.

Role-binding writes follow the same rules (session only, Origin/CSRF, password and configured second factor, `member.manage` at the exact scope). `POST /organizations/{organizationId}/projects/{projectId}/bindings` (200) assigns or changes a project role for an existing organization member, by email. The nested `/environments/{environmentId}/bindings` path does the same for an environment override. `POST .../bindings/{membershipId}/remove` (200) removes the binding at that exact scope. Each answers `{ binding, session? }`, with `binding` null after removal. Organization owners and admins, unknown addresses and non-members answer 404 with no write. An environment-only administrator cannot create or remove an override for a project administrator (SPEC 7). Assignments end the subject's sessions and tokens through their security version. Encrypted retries cover these four routes, and every replay rechecks live `member.manage`.

Token scopes use the closed permission vocabulary in `packages/domain/src/lib/api-token-policy.ts`: profile read, organization/project/environment reads and lifecycle capabilities, billing, members, nodes, deploy, secret write, container exec, volume/database deletion, observability and audit. No wildcard or secret-value-read permission exists. Each scope names a permission and UUIDv7 organization ID, optionally narrowed by project and environment IDs; environment bounds require their parent project. A token cannot span multiple organizations. `profile.read` is the only unscoped account permission. At most 32 input scopes are accepted, copied and deduplicated. Scope matching is never sufficient by itself: the owner's live RBAC policy must also allow the request. Token labels contain 1–64 Unicode code points without control/format characters; expiry is between one minute and ninety days, with at most 50 active tokens per user.

## 8. Public REST API

User-owned API token rows persist only a purpose-bound SHA-256 credential hash, scopes and lifecycle metadata. Password resets and MFA security changes invalidate tokens through the owner's security version; authentication also checks active account status, expiry and revocation. Last-use timestamps advance monotonically. Token lists are owner-filtered and use an exclusive UUID cursor, with at most 100 records per page. Live tenant authorization intersects token scopes with current membership, resource ancestry and environment protection on creation, authentication and private creation replay. Project ownership follows in M2.3e. The account command boundary can accept a transport-authenticated token only when the command supplies its own permission and target. It revalidates the exact token/owner, revocation, expiry, verified account and current authority while holding the account lock through the operation and audit transaction. A token revoked after HTTP authentication therefore cannot enter a subsequent command. Account-only and password/MFA privilege operations reject token contexts. Organization settings, project/environment creation/settings and individual resource reads opt in with command-owned permissions and targets. Their audit actor records the API token id rather than attributing the operation to a browser user. The authenticated transport preserves the credential as a redacted Secret for transactional revalidation. Catalog and membership/binding collections remain session-only: user-visible collection filters alone must not widen a token scope. Resource writes hold the credential owner lock through audit persistence, serializing concurrent revocation; an audit failure rolls back the resource and audit together.

Creating or revoking a token requires password reauthentication and the active MFA factor. Commands recheck the current security version under the user lock; token writes, proof consumption and audit events commit together. Repeating a completed revocation is harmless. Creation verifies every scope against live owner authority and serializes the active-token cap. Listing returns lifecycle metadata without hashes or security versions. A token's plaintext is returned only by creation (or its bounded encrypted idempotent replay).

A token can be bound to one project with `project: { organizationId, projectId }` at creation. Every scope must then stay inside that project or its environments; account-wide and organization-wide permissions are refused. The creator also needs live `member.manage` on the project. The creator remains the owner whose current authority and security version bound every use. Each authentication additionally refuses any target outside the bound project. The composite foreign key deletes the token with its project. Project administrators (`member.manage` on the project) list a project's tokens with `GET /organizations/{organizationId}/projects/{projectId}/api-tokens`, which returns metadata and the creator, never the secret. They revoke any of them with `POST .../api-tokens/{id}/revoke` (204), which requires a session, Origin/CSRF, the password and the configured second factor. Revocation holds the caller's and the creator's account locks in canonical order, so it serializes with the creator's bearer authentication. It changes neither account's security version and is audited with the project's organization. Both routes are session-only.

Bearer authentication re-reads the credential under the owner's lock before intersecting its scopes with current owner authority. Revocation and role/security changes use that same lock. API traffic has separate fixed one-minute quotas: 300 requests per token and 600 per trusted client IP, shared across instances, without the progressive delay used for password proofs. Invalid credentials still consume the IP budget. Creation retries must revalidate the cached credential and owner authority before disclosing it again.

Bearer status codes: a missing, malformed, revoked or expired token, and any valid token on a route that does not accept tokens, gets 401 `authentication_failed`. A valid token whose scopes do not cover the route's exact permission and target gets 403 `api_token_permission_denied`; this check runs before any resource lookup, so missing and hidden resources answer the same way and nothing leaks. Sessions keep the uniform 404 `resource_not_found` for missing or unauthorized tenant resources.

Every controller route must explicitly declare anonymous, account or tenant access; undeclared routes reject even valid credentials. Account declarations cannot authorize routes carrying organization/project/environment parameters. Tenant routes resolve canonical UUIDv7 ancestry exclusively from path parameters and check live resource permissions for sessions. Bearer opt-in must match the declared route permission and receives that same target; request bodies and query strings cannot change authority. A route inventory test checks declarations on every registered controller. Resource HTTP endpoints and route/role acceptance follow in M2.3d3–d4.

[`docs/generated/route-role-matrix.md`](generated/route-role-matrix.md) lists every registered route with its access declaration, its bearer permission and the decision for each fixture role. A unit test regenerates it and fails on any difference. It also checks each `permission@scope` against an independent copy of the section 7 table. An integration test replays every tenant route for every role through the real guards: an allowed read answers 200, an allowed write with an empty body answers 400, and a denial answers 404.

Resource creation/settings retries reuse the five-minute encrypted request/result store through the exported identity HTTP interceptor. Its route allowlist contains only explicit organization/project/environment creation/settings paths; deletion and unrelated paths are rejected. Fingerprints bind the request body, account/security version, credential kind and API-token id. Cached resource results recheck current account, exact credential and live route permission after any storage wait. This check runs only on replay, preserving ordered actor/subject locking inside privilege-changing commands. Resource writes, audits and encrypted retry persistence share one transaction; a storage failure returns no result or session cookie.

Organization writes use `POST /organizations` (201) with name, slug, password and configured MFA proof, and `POST /organizations/{organizationId}/settings` (200) with name/slug. Creation requires a session, returns organization plus public session metadata, and sets rotated credentials only through cookies. Settings accepts the scoped `organization.update` bearer permission or an authorized session. Session writes require Origin/CSRF. Both accept encrypted retries; an old credential cannot replay a creation after ownership rotates the account version, and a different version conflicts with the prior retry fingerprint. The web client must accept the returned session profile and recover lost creation responses through authenticated organization discovery.

Project/environment writes use `POST` on the nested project/environment collection (201) and on each resource's `/settings` path (200). Each accepts authorized sessions or its exact scoped bearer permission: `project.create`, `project.update`, `environment.create` or `environment.update`. Session requests require Origin/CSRF; encrypted retries preserve the original result and audit once. Bodies contain only supported settings; ownership comes from the path. Omitted options use the domain defaults, while nulls, unknown fields and coercible strings are rejected. Settings are complete replacements, including defaulted options.

Resource reads use `GET /organizations`, `/organizations/{organizationId}`, `/organizations/{organizationId}/projects`, `/organizations/{organizationId}/projects/{projectId}`, and the nested `/environments` collection or `/{environmentId}` detail. Collections require a session and accept `cursor`/`limit` (1–100); detail routes additionally accept the matching scoped bearer permission. Unknown collection query fields and malformed pagination are rejected. Metadata includes ISO timestamps and explicit settings, never memberships or credentials. API quotas apply to session reads and are consumed only once for bearer requests already throttled by authentication.

HTTP routes deny bearer access unless explicitly opted in. `GET /auth/session` accepts `profile.read` and returns account metadata with the API credential's expiry; it creates no browser session. MFA and credential-management routes require a browser session. Authorization headers never fall back to cookies; duplicate or malformed headers fail closed. Origin/CSRF checks apply to session mutations and anonymous browser mutations. Explicitly permitted bearer requests use their non-ambient header credential and do not require browser CSRF proof.

Session-only token management uses `POST /api-tokens` (201, secret plus metadata), `GET /api-tokens?cursor=&limit=` (items plus nextCursor, default/max 100), and `POST /api-tokens/{id}/revoke` (204). Creation/revocation require password and optional TOTP/recovery proof when MFA is enabled, Origin and session-bound CSRF; both accept encrypted idempotent retries. A full page returns an exclusive cursor; an exhausted cursor may yield an empty terminal page. Dates require an explicit timezone. A revoked, expired, invalidated or no-longer-authorized token cannot be retrieved from a prior creation retry.

The browser identity transport uses the generated SDK against the current origin only, with same-origin cookies, no response caching and no redirects. Requests time out after twenty seconds and preserve caller cancellation. It reads exactly one matching CSRF cookie (the `__Host-` variant on HTTPS), supplies caller-owned idempotency keys for mutations and never sets bearer credentials. Browser session state retains only user ID, email and expiry in memory. It discards late responses after newer state changes and distinguishes unauthenticated access from temporary service failure. UI errors use fixed messages and bounded retry delays rather than forwarding arbitrary server/transport diagnostics.

Form submissions suppress concurrent requests and retain their retry key for an unchanged body after uncertain transport/server failures. They require an explicit restart after four minutes (before the server's five-minute cache expires), a backward clock change or a replay conflict. Known client rejections release the attempt; HTTP 408 remains uncertain, and HTTP 429 preserves the key because a throttled retry may follow an already-committed command. A bounded server-requested wait survives a form restart. Private retry snapshots live only in native private fields for the form's lifetime, are cleared after success/restart/destruction and cannot appear in object serialization. Leaving or resetting a form invalidates its pending results.

Account forms cover signup, verification, verification resend, login and both password-reset steps. Only active fields participate in validation. Passwords retain whitespace and Unicode code points; new passwords require confirmation. Email and pasted code edges are trimmed, while login accepts either an optional authenticator code or one recovery code. Codes are never read from or written to navigation URLs. Mail-request outcomes remain generic. Successful submissions and route departure clear passwords/codes; abandoned login results cannot populate browser session state.

Web routes are `/auth/login`, `/auth/register`, `/auth/verify-email`, `/auth/request-verification`, `/auth/forgot-password` and `/auth/reset-password`. Public email links `/verify-email` and `/reset-password` redirect to their matching forms. Successful login opens `/account/security`; sign-out returns to login only after server confirmation. Forms use associated labels/help/errors, an error summary, keyboard focus on route/results, optional native MFA disclosure and a content skip link. Navigation moves above the working column on narrow screens. Tailwind and Angular CDK provide the shared styles and programmatic focus primitive, following ADR 0009.

MFA forms distinguish unknown/unavailable status from disabled protection and require current password/proof for the chosen operation. Account security mutations share one submission gate, including sign-out, to avoid overlapping rotations. Provisioning seeds are hidden at their server expiry (with a ten-minute client cap); recovery codes, shown only once by the server, stay visible until acknowledgement or page departure (no timer, WCAG 2.2.1). Successful rotation updates only public session fields. Private grants and inputs clear on dismissal/destruction and serialize as an opaque store label. A setup display timeout hides the seed but preserves a running activation's confirmed recovery-code result.

The account MFA panel supports manual authenticator enrollment with a copyable setup key (time-based, six digits, 30 seconds), activation, recovery-code replacement and disable. Provisioning URIs are not rendered as navigation links. Private text is copied only on an explicit user gesture through the browser clipboard API; denied/unavailable clipboard access offers manual selection and never exposes raw diagnostics. Recovery codes disappear on acknowledgement or timeout. Security-change forms explain session/API-token invalidation before submission, and one shared error summary receives focus when a request fails.

Browser token management retains one metadata page at a time with forward/back cursors, and requires known MFA status before allowing mutations. Creation currently grants only `profile.read`; tenant permission selection follows the live policy adapter in M2.3. The user chooses 1, 7, 30 or 90 days; the absolute expiry is fixed when starting/changing the form, so an uncertain retry preserves the same body/key. Private credentials disappear on acknowledgement, departure or session rotation; no timer hides a token the server shows only once (WCAG 2.2.1). This hides the display without revoking the saved token. Creation/revocation refresh the first metadata page after confirmation. HTTP conflicts use a generic state-conflict message because the same status also covers capacity/state constraints, not only retry-cache conflicts.

The token panel shows permissions, creation/use dates, expiry and status in a keyboard-scrollable table. It keeps the creation credential separate from metadata and requires an explicit copy or acknowledgement action. Session changes clear private token state and refresh metadata, including MFA-driven token invalidation. Expired status updates locally at a thirty-second cadence; revoked, expired and invalidated rows cannot offer an active-token revocation action. Background session/MFA/token loading is registered with Angular pending-task tracking; mutation progress labels belong to the operation that is actually running.

In production, the API serves `dist/apps/web/browser` (override with `WEB_DIST_DIR`) on the browser's public origin. Before listening, it snapshots only index HTML and allow-listed JS/CSS/image/font assets: at most 1,024 directory entries, 16 directory levels, 8 MiB per file and 32 MiB total. Symlinks, missing nonce markers and invalid builds fail startup with opaque diagnostics. Requests never resolve filesystem paths. The fixed `/install/manifest.json` and content-addressed installer/binary paths are additional public build artifacts, bounded separately to 48 MiB per file and 100 MiB total; the manifest is never cached, and these files stay in API memory like the rest of the snapshot (about 36 MiB for both agents). Without HTTPS or those artifacts, the Servers screen still issues join tokens and shows a manual `agent.yaml` setup instead of the install command. Other dotfiles, maps, JSON metadata, traversal paths and the entire `/api` namespace cannot enter the SPA fallback; only GET/HEAD HTML navigation may use it. Hashed Angular bundles receive immutable caching, other public assets five minutes, and HTML remains `no-store` with a new 192-bit nonce on every response. CSP permits same-origin scripts/connections, nonce-bound component styles and Angular's reviewed Trusted Types policies; inline scripts/styles are disabled in the production build. This follows [Angular's CSP and Trusted Types guidance](https://angular.dev/best-practices/security). The development proxy requires `API_PUBLIC_URL` to match the web origin (normally port 4200), preserving the same Origin/CSRF boundary.

A compressed body (any `Content-Encoding` but `identity`, webhooks included) is refused with 415 before it is read: no client sends one, and inflating it would run Node's bundled zlib, brotli and zstd on input anyone can send.
- Applications (PLAN M3.4b1), under `…/environments/{environmentId}/applications`:
  - `POST` with `{config}` creates an application from a `shipkeep.yml` document sent as JSON (201). It needs `deploy.run`, so developers may do it only on unprotected environments (SPEC 7), because the configuration takes effect at the next deployment.
  - `GET` lists the environment's applications, and `GET …/{applicationId}` reads one (`environment.read`).
  - `POST …/{applicationId}/config` with `{expectedConfigSha, config}` replaces the configuration if it still has that hash, otherwise 409 `application_config_changed`. The name cannot change. Saving an identical configuration records nothing.
  - `POST …/environments/{environmentId}/clone` with `{name}` clones an environment (issue #257, browser sessions only, 201): in one transaction a new environment of the same project, with the source's kind, failover policy and protection, and a copy of each application's configuration without `domains`. Nothing else is copied: no secret value, no data, no release or deployment. The copies are not deployed and the secrets they reference show as not set. It needs `environment.read` on the source, `environment.create` on the project and `deploy.run` on the new environment. The new environment is audited as `environment.created` and each copy as `application.created`, both with `clonedFrom`; a taken name is 409 and creates nothing.
  - The web editor validates YAML locally and shows a diff before saving. On 409 it retains the draft, loads the latest version on request, and requires another review before retrying with the new hash. Drafts live only in the component; saving does not start a deployment.
  - Rules:
    - documents are validated against the schema, and errors list JSON pointers and schema messages without input values;
    - only `build.type: image` is accepted until git (M3.1) and Compose (M3.8) sources;
    - the canonical JSON (sorted keys) is limited to 64 KiB and hashed with SHA-256 into `configSha`;
    - a duplicate name in the environment is 409 `application_name_taken`;
    - no application may use the control plane's own name, the host of `API_PUBLIC_URL`: saving, deploying or rolling back a configuration that lists it is 400 `domain_reserved` (ADR 0021; the agent of the machine that hosts the control plane refuses it too);
    - a hostname belongs to one application per organization: saving a configuration syncs its `domains`, and a host another application claims is 409 `domain_taken` (a rollback checks this too). A domain the configuration drops stays claimed while a release of the application with placed replicas still lists it, since its route may still serve it; it is freed when the pipeline stops the last such replicas (after the next deployment, a stop, or a failed deployment's cleanup succeeds), or with the application (#302);
    - wildcard domains are refused with 400 `wildcard_domain_unsupported` until DNS-01 exists.
  - `GET …/{applicationId}/domains` (`environment.read`) looks up each domain live: `public` with its addresses, `private` (only non-public answers, never revealed, so the control plane's resolver cannot be used to map internal names), `none` or `unknown`. It does not connect to the answers. `status` and its values are unchanged.
    - Each domain also has a `match` (PLAN M3.6b1). Every answer, private ones included, is compared with the public addresses declared for the organization's nodes that run the application: not removed, lease not expired, with a placed replica that its agent last saw `running`.
    - `serving`: every answer is such an address. `partial`: only some are. `elsewhere`: none is, or there is no record. `not_running`: no such node runs the application. `unknown`: the lookup failed, or a running node has no declared address, so an unmatched answer could still be its address.
    - The response lists only the DNS answers already shown, never node addresses, so a reader with `environment.read` learns no address that `node.manage` protects.
  - `application.created` and `application.updated` audit events carry the name, source and configuration hashes, not the configuration.
- Deployments (PLAN M3.4b2), under `…/applications/{applicationId}`:
  - `POST …/deployments` (201, `deploy.run`) snapshots the configuration as the next release (numbered per application) and queues a deployment.
    - The plan skips `building` and `built` for image sources, and runs `releasing` only when `release.command` is set.
    - It is refused with 409 `secrets_missing` (listing the names) while a referenced secret is unset, and with 409 `deployment_in_progress` while another deployment is unfinished.
  - `GET …/replicas` (`environment.read`) lists the placed replicas with their node, container and what the agent last saw (`state`, null until seen; `stopReason`, `disk_limit` while a container the agent stopped for its disk budget exists and is `exited` or `dead`, otherwise null; `observedAt`). A change of the stop reason is audited with the observation: every `allocation.observed` event carries `stopReason`, null when there is none.
  - `GET …/deployments` lists the 50 most recent deployments; `GET …/deployments/{deploymentId}` reads one; `GET …/releases` lists the 50 most recent releases (`environment.read`).
  - `GET …/agent-actions` (`environment.read`, issue #263) lists the agent actions the application's deployments requested, newest first, with `cursor`/`limit` (1–100, default 50); `nextCursor` is null on the last page.
  - `GET …/deployments/{deploymentId}/timeline` (`environment.read`, issue #265) reads what one deployment went through: `steps`, its audited state changes oldest first (`from`, null for the first; `to`; `at`; `reason` for `failed`), and `actions`, the agent actions it requested, oldest first, at most 200, in the summaries of `…/agent-actions`, with `truncated` when there are more. The steps are read from the audit log, so a deployment whose audit events are gone has none. Build output is read through `…/build-output` (section 12); the release command's output is not collected yet.
    - Each item has the typed kind, the node (id and name), state, step, attempts, deployment id, times and the summary of SPEC 3.1: `outcome` (`in_progress`, `succeeded`, `refused`, `failed`, `expired`, `cancelled`, `compensated`), `reason` and `result`.
    - The encrypted payload (secret values, registry credentials, confirmation tokens) is never read for this list, and idempotency keys, output tails and agent error texts are never returned.
  - `POST …/deployments/{deploymentId}/cancel` (`deploy.run`) cancels an unfinished deployment through the aggregate. The pipeline (M3.4c) acts on the reported routing outcome.
  - `POST …/deployments/{deploymentId}/rollback` (201, `deploy.run`) deploys a new release copying the pinned image and configuration of the release that deployment ran.
    - The target must have succeeded (or been rolled back) and must not be the release serving now; otherwise 409 `rollback_target_invalid` or `release_already_serving`. A release that never resolved its image answers 409 `release_not_deployable`.
    - The release command does not run again, because migrations of an older version must not be replayed over newer data. Secrets use their current values, and the application's own configuration does not change, so the next deployment uses it again.
    - When the rollback succeeds, the deployment it replaced becomes `rolled_back`, audited as `deployment.rolled_back`.
  - `POST …/applications/{applicationId}/stop` (201, `deploy.run`) queues a stop: a deployment of the release that runs, whose plan has `stop` (section 5.1). It creates no release and needs no secret. `application_not_running` (409) when the application has no placed replica, `deployment_in_progress` (409) while another deployment runs. `stop` is true on that deployment in every deployment answer.
  - `POST …/applications/{applicationId}/maintenance/enter` and `…/maintenance/leave` (201, `deploy.run`) queue a maintenance change (section 5.1, ADR 0025). Like a stop, it creates no release and needs no secret. Refused with 409:
    - `deployment_in_progress` while another deployment runs;
    - `maintenance_already_on` or `maintenance_not_on` when the application already is, or is not, in maintenance;
    - `application_not_running` when it has no placed replica;
    - when entering, `application_without_domain` when its release has no domain, so no route to show the page on, and `agent_outdated` when an agent released before the page (`0.1.0-alpha.1` to `0.1.0-alpha.3`) hosts a replica, with those servers' names in `details.servers`.
    - `maintenance` is `enter` or `leave` on that deployment in every deployment answer, and null on the others. The application's row is locked, as for a deployment, so the two cannot pass their checks at the same time.
    - While the application is in maintenance, a deployment and a rollback are refused with 409 `application_in_maintenance`, so no new release starts behind the page unseen. A stop is allowed.
  - `POST …/applications/{applicationId}/delete` (204, `environment.update`) deletes an application. Destructive: the body carries a `confirmation` token for `application.delete` on this application (section 3.6), spent in the same transaction, and the command is audited as `application.deleted` with the confirmation id.
    - Refused with 409 `application_running` while a replica is placed and 409 `deployment_in_progress` while a deployment runs, so no container is left on a server: stop the application first. A refusal does not spend the confirmation.
    - Refused with 409 `application_cleanup_pending` while a server that is not removed may still hold the application's containers or routes (#474), since its domains go with it and a route may still serve them:
      - while one of its container, route or release-task actions is still under way, nothing more is asked;
      - otherwise, for each container that may be there (created, or sent and not undone, or whose removal was sent and did not succeed, with no later successful removal of that container on that server), and each server whose last route change that may have run is not a successful removal, the deletion asks that server for the removal under a new key, with an hour to do it, audited as `application.cleanup_requested`, and answers 409. It asks only with a confirmation that holds, checked without spending it: a token that does not hold asks for nothing and answers 400 `confirmation_rejected`, and a good one stays usable for the deletion that follows. A removal that fails or expires is asked again by the next attempt.

      An action that never reached its server did nothing. Once each server confirms, the deletion goes through. A server that will not come back is removed (a confirmed action), and its actions then hold nothing.

    - The application's row is locked first, so a deployment queued at the same moment is either seen or refused.
    - Its releases, deployments, stopped allocations and claimed domains are deleted with it by cascade. The audit log and the servers' action history stay; the history loses only its link to the application.
    - The runtime database role may delete rows of `applications` for this command, and of no table that depends on it.
  - Database guarantees:
    - a partial unique index keeps one unfinished deployment per application;
    - releases are immutable: a trigger and the runtime grants allow only recording the image digest, once;
    - finished states and `finished_at` go together (CHECK).
  - `POST …/applications/{applicationId}/exec-sessions` (`container.exec`, M6.1) opens an interactive session in one running replica, with a browser session only: API tokens cannot open one yet. The body is optional: `replica` (numbered from 0, as allocations are; 0 by default), `argv` (`["sh"]` by default, an argument vector never run through a shell: 1 to 64 non-empty UTF-8 entries without NUL, each at most 4 KiB and 8 KiB in all, within the agent's 16 KiB of section 3.3), `tty` (true by default) and `minutes` (1 to 240, 30 by default). It queues the replica's agent an `ExecSession` and answers `201` with the session's `id`, `nodeId`, `attachBy` (one minute later), `endsAt` and `websocketPath` (`/api/v1/exec/{id}`). A replica with no running container seen in the last two minutes answers `409 replica_not_running`, and a person with 4 sessions being opened, waiting or running, or an organization with 32, `409 exec_sessions_limit`; a place is held from the check on, so concurrent opens cannot pass the caps together. The agent action expires with the one-minute join window: an agent that reconnects later never starts the command with nobody there. The session lives in the API process only, so a restart ends it. Audit: `exec.session.opened`, with the program and the number of its arguments, never the arguments, which can carry what the person typed.
  - Audit events: `release.created`, `deployment.queued` and `deployment.cancelled`.
- Image resolution (ADR 0012, PLAN M3.4c2): agents pull only by digest, so the pipeline resolves a release's tag before anything reaches a node. The digest is recorded once on the release.
  - Docker rules name the registry (Docker Hub is `registry-1.docker.io`, with `library/` for single-name images) and `latest` is the default tag. A reference that already carries a digest is used as is, without any request.
  - The control plane sends a `HEAD` for the manifest with the index and manifest media types, without credentials. On 401 it fetches a token from the `Bearer` realm, scoped to `repository:<name>:pull`. When the `Docker-Content-Digest` header is missing, it hashes the manifest as served.
  - Private images (ADR 0019): when the organization stored credentials for the registry of the image, the pipeline reads them in a transaction that ends before the registry is called.
    - They are sent only after the registry answered 401: as HTTP Basic to the token service the registry names, or to the registry itself when it asks for `Basic`. Credentials of another registry are never sent, and Docker Hub's are the ones stored as `docker.io`.
    - The same credentials go with `PullImage` to the node that pulls, inside the encrypted action payload, and expire with the action (one hour).
    - A refusal reports `the registry refused the stored credentials`, or, without stored credentials, that the registry refused anonymous access. Neither message carries the user name, the password or a token.
    - A stored password that does not decrypt (a row altered or moved) fails the deployment with `registry_credentials_unreadable`. Anything else is retried: a database error, also while the organization's data key is read, or a key-encryption key that is not loaded.
    - Agents `0.1.0-alpha.1` and `0.1.0-alpha.2` predate this rule and refuse a pull that carries `docker.io` credentials for a reference without a registry host (`invalid action input`). The control plane therefore sends such a server no Docker Hub credentials: its public Docker Hub images keep pulling anonymously, and a private Docker Hub image needs a newer agent there. Registries named by a host work with these agents.
    - The credentials are found under the name they are stored (`docker.io` for Docker Hub, however the reference writes it) and sent under the name the agent reads in the reference: `registry-1.docker.io/acme/app` gets them with `server: registry-1.docker.io`.
    - An image that is already on the server is not pulled again, so removing credentials stops the next pull, not the containers or the images already there.
  - SSRF guards on every request:
    - HTTPS only, no credentials in URLs, no redirects;
    - IP literals and every resolved address must be public: not loopback, private, link-local, CGNAT, multicast, reserved or documentation ranges, including IPv4-mapped and NAT64 forms;
    - the socket connects to the address that was checked;
    - a 10 s timeout and 1 MiB responses at most.
  - The node holds the same policy at the pull (ADR 0023), since the Docker daemon resolves the registry again, follows its redirects and calls its token service:
    - the daemon goes through `shipkeep-egress` on `127.0.0.1:7480`, which serves `CONNECT` only and connects only to public addresses, checked by its dialer on the address it connects to (the ranges above, kept identical by a test). Its journal (`journalctl -u shipkeep-egress`) names, for each tunnel, the host, the port and the address the socket connected to, and for each refusal its reason with the addresses it was about: those refused as not public, or those that did not answer. A name that resolves somewhere it should not therefore leaves its address in the log, never the request's headers or path;
    - an nftables table, `inet shipkeep_egress`, rejects the new connections of `shipkeep.slice`, the slice that holds the Docker daemon, to loopback, except to the proxy and to the loopback name servers on port 53. Docker loads it before `dockerd` starts, and `nftables.service` loads it in the same transaction as its own ruleset at start, reload and stop;
    - before each pull, the agent reads the daemon's proxy settings (`GET /info`) and refuses the pull (`egress_unguarded`) unless both are the proxy and `NO_PROXY` is empty. An agent started with `--dev` skips this.
  - A server's builds (ADR 0030) run in `shipkeep-build`: rootlesskit (Ubuntu's package and AppArmor profile) starts BuildKit's `buildkitd`, pinned by SHA-256 in `deploy/install.sh`, in a user namespace of `shipkeep-build`, an account in no group that reaches Docker, with 65536 subordinate ids after every range already given, slirp4netns for its network and the host's loopback out of reach. Its socket, `/run/shipkeep-build/buildkitd.sock`, is for the `shipkeep-build` group, which the agent's account is in. It runs in `shipkeep-build.slice` (half the memory at most, CPU weight 50) with `OOMScoreAdjust=1000`. Between builds, BuildKit's garbage collection keeps its cache within 20 % of the disk, and frees it when less than 15 % is left; a build in progress is not bounded by it (open question).
    - The `build` chain of `inet shipkeep_egress`, matched on the account's id, lets new connections reach public addresses on any port, the name servers of `/etc/resolv.conf` on port 53, and the server's own addresses on port 443 only; it rejects the server's other own addresses and the proxy's ranges, which a test keeps identical, with IPv4-mapped addresses. The builder loads the table before it starts.
  - Failures report `image_resolution_failed` with the registry and the status, never tokens. Registries on private networks are not supported yet (open question).

### 8.1 Identity security parameters

- Account endpoints are `POST /auth/register`, `/auth/verification/request`, `/auth/verify`, `/auth/reset/request`, `/auth/reset`, `/auth/login`, `/auth/logout` and `GET /auth/session`, under `/api/v1`. Signup and mail requests return an empty 202 regardless of account existence/status. Codes are submitted in JSON bodies. Without SMTP configuration, mail requests fail with 503 before account creation. Anonymous browser mutations require the exact `API_PUBLIC_URL` Origin; session mutations also require `X-Shipkeep-CSRF` matching the CSRF cookie. All responses use `Cache-Control: no-store`; JSON/form bodies are capped at 16 KiB (larger only on the secret and application writes of section 8). `TRUST_PROXY=none` is the default; `loopback` is available only when the local reverse proxy overwrites forwarding headers and the API is not exposed through another proxy. A single IP address is the third form, never a range or a list: on a single machine (ADR 0021, `deploy/control-plane/compose.single-machine.yml`) the server's Caddy reaches the API through the gateway of the control plane's Compose network, `172.31.250.1`, whether Docker's userland proxy is on or off, and that address alone is trusted.
- An account lists its sessions with `GET /auth/sessions` and ends another one with `POST /auth/sessions/{sessionId}/revoke` (issue #253), browser sessions only, with Origin/CSRF. The list holds the sessions that still sign requests in (not revoked, not expired, not idle, created no later than the request, at the account's security version), the 100 most recently active first, with `truncated` set when more exist, each with its address, its creation and last activity times, and the browser and system read from its User-Agent among known names, never the header itself; the current one is marked. Ending one sets `revoked_at`, so its next request answers 401, and is audited as `identity.session_revoked` with the account as actor and no organization. The current session cannot be ended there (409 `session_current`): signing out ends it. Another account's session, an ended one and an unknown id answer 404. `POST /auth/sessions/revoke-others` ends every other live session of the account at once, listed or not, answers `{ revoked }` and, when it ended any, is audited once as `identity.sessions_revoked` with the count.
- Account pre-hijacking defence: `POST /auth/verify` takes the verification code and the password chosen at registration. The code proves the mailbox; the password proves the person verifying is the one who registered, so nobody can register someone else's address and wait for the owner to activate it. Password reset works on pending accounts as well as active ones and activates a pending account: the mailbox owner can always claim an address someone else registered first, which also invalidates the earlier password, links and sessions.
- Email identities use lowercase ASCII mailboxes (maximum 254 characters, local part 64); PostgreSQL `citext` enforces case-insensitive uniqueness. Internationalized and quoted mailboxes are outside v0.1.
- An account may carry a display name (issue #251), chosen at registration (`name`, optional) or later with `POST /auth/profile` (browser session, Origin/CSRF; an empty name removes it). It is normalized to NFC, trimmed and has its runs of white space collapsed to one space; it holds 1 to 64 code points and no control, format or line/paragraph separator character, otherwise `400 display_name_invalid`. `GET /auth/session` and the organization's member list return it. The interface names a person by it; without one, by the part of the address before the @, with the address itself shown beside it where it was. The audit log and the actor of a deployment or event show the name, or the address without one, for the organization's current members (read from its member list, up to 20 pages); any other account, such as a former member, shows as `user`. A change is audited as `identity.profile_updated` with the account as actor, no organization and only `set` or `removed` in the payload, never the name; an unchanged name writes nothing.
- Passwords contain 15 to 128 Unicode code points, without trimming, normalization or composition requirements. NUL is rejected. Argon2id v19 uses 64 MiB, three iterations, one lane, a random 16-byte salt and a 32-byte hash. At most two hashes run concurrently per process, with at most 16 waiting callers; overload fails closed.
- Session, verification, reset and API credentials have 256 random bits. Only SHA-256 hashes with a distinct `shipkeep:<purpose>:` prefix are persisted. Email verification expires after 24 hours; password reset after 30 minutes. Session limits remain 12 hours idle and seven days absolute, with equality at either boundary considered expired.
- TOTP uses RFC 6238 SHA-1, a random 160-bit secret, six digits and a 30-second period. Accept the current time step and one adjacent step in either direction. Persist the accepted counter atomically and reject counters already consumed. Ten random 128-bit recovery codes are shown once and stored as purpose-bound hashes; each is consumed atomically.
- Pending TOTP enrollment expires after ten minutes and is tied to the account security version; a password reset invalidates it. The database stores either a pending or active encrypted seed, never both. Activation requires an active account and a current pending version. Disabling MFA removes its recovery hashes; counter and recovery claims join the user's audited transaction so a failed command cannot consume a proof.
- MFA setup and activation require current-password reauthentication; disabling MFA and replacing recovery codes additionally require a fresh TOTP or unused recovery code. Activation, disablement and recovery replacement increment the security version, revoke all older sessions/reset links and return a fresh session atomically. Login grants no session until the active second factor succeeds. Password reset preserves MFA and its recovery mechanism. Recovery use and all MFA management commands are audited without secret values.
- MFA HTTP routes are `GET /auth/mfa` and `POST /auth/mfa/setup`, `/enable`, `/disable`, `/recovery`. Status returns only enabled/pending state and the remaining-code count. Setup returns private provisioning data; activation/recovery replacement return ten private codes, always with no-store headers. Login accepts either `totp` (six digits) or `recovery` (32 lowercase hex characters). MFA mutation limits use the authenticated user ID as well as IP; changing IP does not reset the account limit. Authenticated retry snapshots bind user ID and security version. After credential rotation, retries with a different security context conflict; a user who loses the recovery-code response can sign in with TOTP and regenerate codes after reauthentication.
- TOTP provisioning URIs are secret response data, never navigation URLs or log fields. Secret values stay wrapped until hashing, encryption or an explicitly defined delivery boundary.
- Identity email requires SMTP with implicit TLS (normally port 465), certificate-chain and hostname verification, and TLS 1.2 or newer. Configure `SMTP_HOST` and `SMTP_FROM`, optionally paired `SMTP_USER`/`SMTP_PASSWORD` and a public `SMTP_CA_FILE` for a private issuer. STARTTLS/plaintext SMTP is not supported in v0.1. Delivery has a ten-second inactivity timeout and a twenty-second total deadline. Emails contain a clean page link and a code to paste; the bearer credential is never embedded in a navigation URL. `API_PUBLIC_URL` is an origin without credentials/query/fragment and must use HTTPS in production.
- Email is optional (ADR 0020). Without `SMTP_HOST` the installation sends nothing, and:
  - `POST /auth/register`, `/auth/verification/request` and `/auth/reset/request` answer `409 email_not_configured`, the same for every address: the refusal comes after the Origin check and the parsing of the body, and before the attempt limit, the replay of a stored answer and the validation of its fields. A body that is not well-formed JSON is a `400` as everywhere else;
  - `GET /auth/options` is public and answers `{ "email": false }` (`true` with SMTP). It says nothing about any account. The sign-in screens read it: without email they offer neither sign-up nor a reset link, and say that the administrator of the installation creates accounts and resets passwords;
  - only the control plane that serves requests delivers queued mail; the command line below never takes a mail job;
  - accounts are created on the server that runs the control plane, by its command line: `node main.js account create --email <address>` creates an account that is active at once, and `node main.js account reset-password --email <address>` gives one a new password. The password is typed without echo on a terminal or is the first line of a pipe, never an argument or a variable. The list of commands is closed, and nothing listens while one runs: no HTTP port, no agent gateway, no worker. A command writes one line that says what was done, on standard output, or on standard error when standard output cannot take it (a reader that closed its pipe): the change is committed by then, so the command still succeeds. For the same reason, an application that does not close cleanly changes neither a success nor the reason of a refusal: after a success it is a warning on standard error, and when standard error is a pipe whose reader stopped reading, the command stops waiting for it after two seconds; after a refusal nothing is added to the reason;
  - a command that cannot be read exits with status 2, `account create` for an address that already has an account with status 3 (an installer resuming its own run keeps that account, password included), and any other refusal with status 1;
  - for the single-machine installer (ADR 0021), three more commands read no password: `node main.js organization create --name <name> --slug <slug> --owner <address> [--id <uuidv7>]` creates an organization owned by an active account and says its id. Given `--id`, a UUIDv7 like every tenant id, chosen and recorded by the installer first, it is idempotent, also against a concurrent call: when that organization exists with the same slug and owner, it says the same id and changes nothing, so that a resumed installation finds it again; another slug or owner is refused; `node main.js server join-token --organization <id>` issues a join token for it and writes the token alone, and only to a standard output that is not a terminal (a file or a pipe into the agent's token file), never to standard error; `node main.js server ca-fingerprint` says the installation CA's fingerprint. Creations and tokens are audited with the system as actor;
  - a reset advances the security version (sessions, API tokens and pending links stop working), activates an account that never confirmed its address, refuses a disabled account, and leaves a second factor as it is. On a terminal, Backspace removes one Unicode code point, whatever its size in bytes (a letter typed as a base letter and a combining accent loses the accent only);
  - `email_verified_at` is set at creation: the address is confirmed by the operator instead of by its mailbox, and nothing checks that the mailbox exists;
  - audit events `identity.created_by_operator` and `identity.password_reset_by_operator`, with the system as the actor, and `identity.activated_by_operator` before the latter when the reset activated the account.
- Authentication limits are persisted in PostgreSQL per operation, on three axes: client network (an IPv4 address or an IPv6 /64), subject, and subject from one client network. Credential operations allow 100 requests per network and ten per subject and network in 15 minutes; the subject alone has no hard cap, so failures from elsewhere can never lock its owner out, but every credential attempt on a subject is spaced by 250 ms doubling up to 8 seconds (up to 64 seconds per subject and network). Signup and email requests allow 20 per network and five per subject per hour; that per-subject cap is kept on purpose to prevent mailbox flooding. Rejected retries do not extend a block. Successful login clears its account delay and that network's account quota, never the network quota. Expired buckets are removed in bounded batches. The HTTP layer returns the applicable quota and retry delay; it must normalize subjects and derive IPs from explicitly trusted proxy configuration.

## 9. Secrets

- Envelope encryption. A key-encryption key (KEK) lives in `/etc/shipkeep/kek` (0400, owned by the service user; 32 raw bytes or their base64) or an external KMS later. Each environment has a data-encryption key (DEK) stored encrypted by the KEK (`DataEncryptionKey`, scope `environment:<id>`). Values are encrypted with AES-256-GCM using the DEK, with associated data that binds the ciphertext to its scope and purpose (`shipkeep:data:<scope>:<purpose>`); blob layout `0x01 | nonce(12) | tag(16) | ciphertext`. The API refuses to start when the KEK file is readable by group or others.
- Secrets are sent to agents only inside `CreateContainer` and `RunReleaseTask`, over mTLS, and passed to containers as environment variables (default) or as files on a tmpfs mount (`secrets_as_files: true`).
- The agent never writes secret values to its SQLite database or its own files; the journal stores a hash of the payload and `desired` stores secret references only.
- Known limitation, documented for users: Docker itself persists a container's environment variables in its container configuration on disk (readable by root only). This is what lets Docker restart a container after a crash or a reboot without the control plane. With `secrets_as_files: true` nothing is persisted, but after a node reboot those containers can only start once the agent has fetched the values from the control plane again.
- The API never returns secret values after creation. The UI shows names, versions and who changed them.
- HTTP:
  - `GET …/environments/{environmentId}/secrets` lists names, versions, author and dates (`environment.read`).
  - `POST …/secrets` with `{name, value}` creates version 1 or stores the next version (`secret.write`).
  - `POST …/secrets/{name}/remove` removes a secret (204).
  - All three accept sessions or scoped tokens, and writes have no encrypted retry.
- Rules:
  - names match `^[A-Z_][A-Z0-9_]{0,127}$`, and values are 1 byte to 64 KiB without NUL;
  - developers may write only unprotected environments (SPEC 7);
  - each value is encrypted with the environment DEK and bound to its name and version;
  - concurrent writers are serialized by a version compare-and-swap;
  - `secret.set` and `secret.removed` audit events carry the name and version only.
- Rotation of the KEK is a documented admin command that re-encrypts DEKs.
- Registry credentials (`modules/registries`, ADR 0019), write-only like secrets and managed with `organization.update`:
  - `GET …/organizations/{organizationId}/registries` lists the registry host, the user name, the version, the author and the dates.
  - `POST …/registries` with `{server, username, password}` stores the credentials of one registry, or replaces them (200). `server` is a host and an optional port; a URL, a path or embedded credentials answer 400 `invalid_registry_server`. The user name holds no colon and no control character (it travels in HTTP Basic). `docker.io`, `index.docker.io` and `registry-1.docker.io` are stored as `docker.io`.
  - `POST …/registries/{registryId}/remove` removes them (204). A removal that meets a concurrent removal or replacement answers 409 `registry_credentials_changed` and removes nothing.
  - An organization stores credentials for at most 100 registries; one more answers 409 `registry_limit_reached`. The list returns them all.
  - The password is encrypted with the organization's data key, bound to the host and the version. Audit events `registry.credentials_set` and `registry.credentials_removed` carry the host, the user name and the version.
- The installation's own registry (ADR 0030, #215) is CNCF Distribution with token authentication; the control plane is its token service.
  - Each application has its repository, `{organizationId}/{applicationId}`, under the control plane's public host (`API_PUBLIC_URL`'s host, which is also the token's audience and Distribution's `service`).
  - An action that pushes or pulls carries a grant: a user name `{organizationId}.{grantId}` and, as its password, a random secret of 32 bytes (base64url), valid until the action's deadline. A build's grant pulls and pushes; a deploying server's only pulls. Only the secret's SHA-256, bound to its purpose as API tokens are, is stored (`registry_grants`), and each grant is audited as `registry.grant_issued` by the system, with the repository, whether it pushes and its deadline. Grants expired for a day are removed when the organization is issued another one.
  - `GET /api/v1/registry/token?service=…&scope=…` (anonymous, rate limited as API requests) takes the grant in a basic authorization header and answers `{token, access_token, expires_in, issued_at}`, with `cache-control: no-store`. The token is a JWT signed with the installation's Ed25519 registry key (`alg: EdDSA`, `kid` the SHA-256 of the key's SPKI encoding), issued by `shipkeep` for the control plane's host, valid five minutes and never past the grant's deadline. Of the scopes asked (at most eight), it grants only the grant's repository, with pull, and push when the grant allows it; anything else is left out, and Distribution then refuses it.
  - Any other request (no or another scheme, a malformed user name or password, an unknown grant, a wrong password, an expired grant, another service) answers the same 401 with `WWW-Authenticate: Basic realm="Shipkeep registry"`: the answer never says what was wrong.
  - The registry key is an installation key like the CA's (`installation_keys`, kind `registry`, audited when created). At start, the control plane writes its public half as a JWKS to `REGISTRY_JWKS_FILE` when set, in one rename, for Distribution's `auth.token.jwks`.
  - Distribution (`registry`, `deploy/control-plane/registry.yml`) runs in the control plane's Compose project, with its images in the `registry-data` volume and the JWKS in `registry-auth`, which the control plane writes and the registry only reads. It starts once the control plane is healthy, so the key it reads at start exists. Its API is served on the control plane's name under `/v2/`, uncompressed: by the Compose Caddy on a separate machine, and on a single machine by the server's Caddy, through a route the agent keeps before the control plane's (`shipkeep-control-plane-registry`, path `/v2` and `/v2/*`, to `control_plane.route.registry`, `127.0.0.1:5000` by default, where `compose.single-machine.yml` publishes it). No action can name or remove that route.
  - Image retention (ADR 0030): every day at 02:30 UTC, a pg-boss job of the control plane reads the registry's catalog (`REGISTRY_URL`, `http://registry:5000` in Compose) with tokens it signs for itself, `subject` `shipkeep-retention`: `registry:catalog:*`, then `pull` and `delete` on one repository at a time. Of each application's repository it keeps the tags that the six releases last deployed with success run (recency is that of their last successful deployment, so the release a rollback serves is kept; a rollback's copy runs its source's tag) and those every release a deployment still runs for runs, and deletes every other tag, one at a time and never a manifest: a manifest another tag names stays, even a tag pushed after the read. The tags are read before the releases, so the release of a tag read is already recorded; a deployment queued after the read is a new release with a tag of its own, or a rollback to the release before the one that serves, which is kept. The catalog and the tags are read to their empty last page, and a repository with more than 10,000 tags is left alone. The repository of an application that no longer exists is emptied. Each application's removals are audited as `application.images_pruned` (`tags`, `count`), those of a run where another tag failed included; if the audit itself fails, the log keeps the tags removed. A repository or a tag that fails is left for the next day. Only names `<organization>/<application>` are touched. Distribution's garbage collection removes the manifests no tag names, with their layers.
  - Every deployment of the organization whose image comes from that host uses them, for the digest lookup and for the pull (SPEC 8, image resolution). Nothing in `shipkeep.yml` refers to them.
- The GitHub App of an organization (`modules/git`, ADR 0031), created through GitHub's manifest flow by an owner (`integration.manage`), with a session only:
  - `POST …/organizations/{organizationId}/github-app/manifests` with `{owner: "user"}` or `{owner: "organization", githubOrganization}` answers 201 `{url, manifest}`: the browser posts `manifest` to `url` on github.com. The App is private, named `Shipkeep <slug> <6 random characters>` within GitHub's 34 characters, with the permissions and the `push` event of ADR 0031, its webhook on `/api/v1/webhooks/github/{organizationId}`, and GitHub sending the owner back to `/orgs/{organizationId}/integrations/github`. The flow's state is 32 random bytes in the URL, stored as its SHA-256 with the owner and an expiry of one hour; a new flow replaces the one under way. An organization that has an App answers 409 `github_app_exists`.
  - `POST …/github-app` with the `{code, state}` GitHub sent back stores the App (201). The state must be the flow's, the owner's and unexpired, checked before GitHub is called and again, under the transaction, when the App is stored; otherwise 400 `github_app_flow_invalid`. A code GitHub no longer knows is `github_app_flow_invalid`, and any other failure of GitHub a 503 that does not repeat its text. Once GitHub has answered, the App exists there: if it cannot be stored (an answer that fails a field check, a flow replaced meanwhile), the answer is 409 `github_app_not_connected` with the App's page in `appUrl`, for the owner to delete it on GitHub before starting again.
  - The private key, the webhook secret and the client secret are encrypted with the organization's data key and bound to the App's identifier and to what each one is; no route returns them, and the runtime role can only read and add Apps. `GET …/github-app` (`organization.read`) answers `{app}`, null without an App: its identifier, slug, name, owner account and page on GitHub.
  - Audited: `github.app_flow_started` (the App's name and the GitHub organization, if any) and `github.app_created` (identifier, slug, name, owner account).
  - Webhooks: GitHub delivers to `POST /api/v1/webhooks/github/{organizationId}`, an anonymous route marked `AllowSignedBody`: a server calls it, not a browser, so it carries no Origin, and the `X-Hub-Signature-256` HMAC of the raw body with the App's webhook secret is checked in constant time before the body is parsed. The body is read raw, at most 1 MiB (413 beyond). A wrong or missing signature, an organization without an App and a ping of another App answer 401 `github_webhook_rejected` alike; malformed headers or payloads 400 `github_webhook_invalid`. Accepted deliveries answer 204.
  - Each delivery's `X-GitHub-Delivery` identifier and the SHA-256 of its body are recorded, both unique per organization, in the transaction that applies the delivery, and kept 30 days. A delivery whose identifier or body was recorded answers 204 and does nothing: GitHub signs the body, not the identifier. One that failed is recorded nowhere, and GitHub's redelivery is processed. These rows are replay bookkeeping, not organization state: a delivery is audited by what it changes.
  - `installation` and `installation_repositories` events keep `github_installations` (account, `all` or `selected` repositories, suspension) for installations of the organization's own App. A change applies only when GitHub's `updated_at` for the installation is newer than the last one applied, at most five minutes ahead of the control plane's clock. At the same time, only a removal or a suspension of an active installation applies: the state kept is never the less restrictive one. An installation suspended and unsuspended within one second therefore stays suspended here until its next change on GitHub. A change for an installation not recorded yet, its creation lost, records it. One installation's deliveries apply one at a time (a transaction lock per organization and installation, its first delivery included), so an older change never writes after a newer one. A removal applies whatever its time and leaves a tombstone (`deleted_at`): GitHub never brings an installation back, since installing the App again makes a new one, so no later delivery for it changes anything, even once its delivery records are forgotten. Tombstones are kept until the organization is deleted: one small row per installation of its own App ever removed. Expired delivery records are removed with `SKIP LOCKED`, so a delivery waiting for its installation never holds up the others. Changes are audited as `github.installation_added`, `_removed`, `_suspended`, `_unsuspended` and `_repositories_changed`, with the system as actor and the GitHub sender's login. A verified `push` to a branch (not a tag, not a deleted branch) is recorded with a job of the `github-push` queue, in one transaction, and answered at once: a delivery whose job was not stored is recorded nowhere either, and GitHub's redelivery is processed (#213).
  - The job takes the Git applications of the organization that follow that branch of that repository through that installation, 20 at a time in identifier order: a full page sends a job for the next one at once, so a push reaches every one.
    - It asks GitHub for the branch's head, with a token for that repository, and goes on only while the pushed commit is that head: a replayed or overtaken push deploys nothing.
    - It reads shipkeep.yml at that commit and makes it the application's configuration, as the system (`application.updated` with `commitSha`), with the commit and the repository's name as GitHub answers them: the same configuration at another commit is recorded too. The application's name cannot change.
    - The application is then locked and the environment's protection read again, since GitHub was asked meanwhile. If another push changed the application after this one listed it, this one is tried again rather than applied over it: GitHub may have answered the other one later. Unless the environment is protected or the application is in maintenance (`deployment.push_held`, with the reason, targeting the application), it queues a deployment with the trigger `webhook` and no actor. A protected environment holds the push before anything only a deployment needs is checked, such as its secrets being set. Its release keeps the commit (`commit_sha`); `release.created` and `deployment.queued` are the system's, with `commitSha` and the pusher's GitHub login (`githubPusher`). A release deployed by hand keeps the commit the configuration was read at.
    - A configuration that cannot deploy is audited as `deployment.push_refused` with the error's stable code, never its text.
  - While a deployment of the application is under way, or GitHub cannot be reached, the push is tried again a minute later, 30 times at most, for the applications left; then it is audited as `deployment.push_refused` with the code `push_given_up`. A deployment queued at the same moment rolls the push's release and configuration back, and the push is tried again. A push handled again deploys nothing twice: when the newest release is already the commit's, nothing is queued.
  - New environments are protected (SPEC 7), so by default a push only updates the configuration; an administrator deploys it, or makes the environment unprotected.
  - An application can take its configuration from a repository (`source: git`, #213): `POST …/environments/{environmentId}/applications/github` (`deploy.run`) with `{installationId, repositoryId, branch, configPath}` creates it from the shipkeep.yml at the branch's head (201). `configPath` defaults to `shipkeep.yml`, and must be a relative path to a `.yml` or `.yaml` file of at most 255 bytes with no empty, `.` or `..` segment; the branch follows `git check-ref-format`. Both are checked before GitHub is asked.
    - The installation must be one of the App's, reported and not suspended (400 `github_installation_unavailable`). Without an App the answer is 409 `github_app_missing`.
    - The control plane mints a token for that one repository with `contents: read` and `metadata: read`, and revokes it once read. It finds the repository by GitHub's identifier: a renamed repository is the same one, and its new name is kept. A repository the installation does not reach is 400 `github_repository_unavailable`, an unknown branch 400 `github_branch_not_found`, a missing file 400 `github_config_not_found`.
    - The file is at most 256 KiB, parsed and validated like any configuration, with the commit in the error details (`invalid_application_config`). Until builds land (M3.3), it names a built image: another `build.type` is 400 `unsupported_build_type`.
    - The application keeps the installation, the repository's identifier and name, the branch and the path. Its configuration is the repository's: `POST …/config` answers 409 `application_config_in_repository`. `application.created` carries the repository, the branch, the path and the commit read.
    - An environment holding a Git application cannot be cloned yet (409 `environment_has_git_applications`): see the open questions.
    - Its file, as the repository holds it now (#214): `GET …/applications/{applicationId}/repository-config` (`environment.read`) reads it at the branch's head with a read token, and answers the repository's name, the branch, the path, the head's commit, the file's blob `sha` and text, the commit the application last read (`appliedCommitSha`), whether the file is a valid configuration for this application (`valid`, same name), and whether the application's configuration is the file's (`applied`: false is drift). An application that runs an image answers 409 `application_not_from_repository`.
    - A change, before it is written: `POST …/repository-config/preview` (`deploy.run`) with `{config, blobSha}` validates the whole document like `POST …/config`, with the same name, and answers the file's text with the change (`changedText`) and its changed lines with three around each (`diff`, longer unchanged runs counted as `skipped`). The file changes as little as can be: an edited value keeps its line and its comment, an added key goes at the end of its map, a removed key goes, a changed list is written again whole; nothing is folded, and CRLF and a missing final line break stay. A `blobSha` that is no longer the file's answers 409 `config_file_changed`, a file that is not a YAML map 400 `invalid_config_file`, and a change that would take the file over 256 KiB 400 `config_file_too_large`: the text written must read as a configuration, within the file's size. `valid` is false too for a file naming the control plane's own domain, which a change of it would be refused for. Writing the change, as a pull request or a commit, comes next (#214).
    - Writing it: `POST …/repository-config/changes` (`deploy.run`, a browser session only) takes the same body and writes the same text to the repository, with a token for that one repository with `contents: write` and `pull_requests: write`, revoked once used (ADR 0031). By default, or when the project's `gitWriteMode` is `pull_request`, it creates a branch `shipkeep/config-<12 hex>` at the head the change was read from, commits the file there and opens a pull request into the application's branch. With `commit`, it commits on the branch itself; a commit GitHub refuses on an unchanged file, as a protected branch does, becomes a pull request. The head's file is checked again first: a blob other than `blobSha`, before or at the refusal, answers 409 `config_file_changed` and nothing more is written. A change that leaves the file as it is answers 400 `config_unchanged`, and a branch or pull request GitHub refuses 409 `repository_refused_change`. The commit and the pull request carry the application's name and no person: the repository may be public. It answers 201 `{via, commitSha, url}`, with `number` and `branch` for a pull request, and is audited as `application.config_written` (the repository, the branch, the path, the commit read, where it went). GitHub cannot take a change back: if the audit store fails after the write, the answer is still the change written, and the log keeps the event without the store's error, so that a retry does not write it again. An `Idempotency-Key` (lowercase UUIDv4 or v7) makes a retry with the same body answer the first answer, kept encrypted for five minutes, and write nothing; a body over 16 KiB is matched by its SHA-256. The text written must read as a configuration within 256 KiB, like the preview's. Shipkeep's configuration does not change: the push to the branch applies it, like any other (SPEC 7).
  - The App calls GitHub as itself with a JWT it signs with its private key (RS256, issued a minute back, nine minutes long), and through installation tokens scoped to what each call needs. `GET …/github-app/repositories` (`organization.read`) lists the repositories of the App's installations that are not suspended: one JWT and one token per installation, the token with `metadata: read` only and revoked once read, at most 500 repositories sorted by name (`truncated` when the listing stopped there with pages or installations left). Each answer is `installationId`, `id`, `fullName`, `defaultBranch` and `private`; an installation GitHub does not answer for (removed or suspended there, its delivery lost) is listed in `unreachable` without hiding the others, and when none answers the route is a 503. A listing is reused for a minute while the installations stay the same. Repository names are GitHub's, never `.` or `..`; branch names follow `git check-ref-format`, any script included; an entry that breaks either is left out. Without an App the list is empty. GitHub's answers are checked entry by entry, bounded to 2 MiB, never followed through a redirect, and any failure is a 503 that does not repeat GitHub's text.

## 10. Backups

- Targets: any S3-compatible storage. Credentials tested on save.
- Databases: engine-native logical dumps (`pg_dump -Fc`, `mysqldump --single-transaction`, `mongodump --archive`, Redis `BGSAVE` + RDB copy), streamed through client-side encryption (age, per-target key) to S3.
- Volumes: `tar` stream of the volume, encrypted the same way. Consistent snapshots for databases use the dump path, not volume tar.
- Schedules in cron syntax with retention (`keep` count). Restore to the same or another node, into the same or a new volume or database.
- Every backup records size and SHA-256. A weekly automatic restore test into a scratch container is available as a policy.
- Instance backup (ADR 0026): control plane PostgreSQL (the CA is in it) and the KEK, in one age archive encrypted to the operator's public key, made and restored with `deploy/control-plane/backup.sh`. Its plaintext is a manifest line (format, version, creation time, newest migration, KEK, and an HMAC of those under a key derived from the operator's identity, which `keygen` leaves on the server), then `pg_dump --format=custom`; no plaintext dump is written to disk. A restore asks for confirmation, refuses an archive whose HMAC does not match the identity it is given before any of it reaches `pg_restore`, stops the control plane, restores the database into a new one in one transaction, ends every session and unused email link in it, which takes the place of the current database once complete (the current one is kept under another name), then replaces the KEK (the previous one is kept beside it); a backup from a newer version is refused. S3 destination (M5.4b): `./backup.sh create --s3 | list | check` and `restore s3:NAME`, with any S3-compatible storage set in `.env` (`SHIPKEEP_BACKUP_S3_*`, HTTPS only unless plain HTTP is said explicitly). The archive is uploaded in parts straight from the encryption, by a separate container (`backup-transfer`) that has the network and never sees the key or anything in clear. An archive is never replaced, by a conditional write (`If-None-Match: *`), and each name has a random part. An archive this run stored while its dump or encryption failed is deleted, best effort: if that fails, the script names it. A refused or failed upload never leads to a deletion.

## 11. Previews

- Enabled per application in `shipkeep.yml`. Triggered by PR open and push; destroyed on PR close or TTL expiry.
- Each preview is an `Environment` of kind `preview` cloned from its parent's variables (secrets opt-in per name).
- Hostname: `<app>-pr-<number>.<preview-domain>` (single label, compatible with wildcard certificates).
- `database: clone` restores the parent's latest backup into a new database; `empty` creates a fresh one; `none` reuses nothing.
- `max_active` enforced; the oldest preview is not evicted automatically, the new one is rejected with a PR comment.

## 12. Observability and alerts

- Logs (ADR 0029): labels `org`, `project`, `env`, `app`, `instance` (the replica), `node`, `stream`. Search by label and full text. Retention 30 days.
  - Build output (ADR 0032): an entry carries the build action's `action_id` and no container. The control plane accepts it only for a `buildImage` action it queued on that node with a deployment's key (`d:<deployment>:…`), and labels it with that deployment's application, environment and project, `instance` and `stream` `build`, and the field `deployment`. An application's log search never returns build lines (`-stream:=build`). The agent keeps the lines not acknowledged yet, at most 8192 lines and 8 MiB, the oldest dropped first, and sends them again on the next stream; a build never waits for them.
  - The agent follows each managed container's output through Docker's logs API from a cursor per container, the timestamp of its last acknowledged line, kept in its local state. After an outage or a restart it reads again from the cursor: a line may arrive twice, and none is lost while Docker's `json-file` files still hold it.
  - An entry is a container name, `stdout` or `stderr`, Docker's timestamp and the line, cut at 16 KiB (and marked so), with bytes that are not UTF-8 replaced by U+FFFD. The values of the container's secret environment variables of 8 bytes or more are replaced by `[redacted]` before sending; secrets mounted as files are not. The agent sets the `sk.secret_env` label on every container it creates, empty without secrets; a container without it predates the label, and every environment value of 8 bytes or more is redacted from its lines until the application is redeployed (a release creates new containers, with the label). Each line of a multiline value is redacted on its own, CRLF included, when it has 8 bytes or more. A line cut at 16 KiB that ends with the start of a value, 8 bytes or more of it, loses that start too.
  - The control plane maps each container name to the node's placed allocation, drops what maps to nothing, sets the labels itself, and accepts 512 KiB per second per node with bursts of 4 MiB, past which acknowledgements wait. A batch is charged before anything is looked up: the UTF-8 bytes of all its lines, kept or dropped, and at least 16 KiB. VictoriaLogs is a service of the control plane's Compose project, on its internal network only, pinned by digest.
  - Without `VICTORIALOGS_URL`, Welcome's `logs` is false and agents ship nothing; a `ShipLogs` stream is refused with `FAILED_PRECONDITION`, as is one whose first frame is not `LogsOpen` with the node's current lease epoch. A batch numbered out of order ends the stream with `INVALID_ARGUMENT`, and one the store did not keep with `UNAVAILABLE`, without its acknowledgement: the agent sends again from its cursor. Malformed entries (a container name outside the agent's grammar, a stream other than stdout or stderr, no time, a line over 16 KiB) are dropped, as are entries of containers that are not the node's placed allocations; the rest of the batch is written and acknowledged.
  - A line keeps Docker's timestamp, so one sent again after an outage lands at its own time. A timestamp more than five minutes ahead of the control plane's clock is replaced by that clock; a line older than the 30 days of retention is dropped. A search shows once a line sent twice: same time to the nanosecond, replica, stream and text.
  - The API answers a search and a live tail for one application with `environment.read`: `GET …/applications/{applicationId}/logs` takes `text` (at most 256 characters the lines contain, matched with their case), `stream` (`stdout` or `stderr`), `instance` (the replica), `from` and `to` (with their offset; the last hour by default, 30 days at most), `limit` (200 by default, 500 at most) and `order` (`newest`, the default, or `oldest`). It answers `kept` (false without a log store) and `lines` in that order, each with its `time` (RFC 3339 with nine digits of fraction, Docker's own), `stream`, `instance`, `line` and `truncated`. The live view reads `oldest` first from three seconds before its newest line, so that a line another server sent late still shows, and again at once from the last line read while an answer is full, so that a burst is not skipped; `from` with up to nine digits of fraction is used to the nanosecond, moved to UTC when written with an offset. It stops asking once the installation says it keeps no logs. A failure of the store, or an answer that breaks or passes 16 MiB, is a `503` whose text says nothing of it. User text is a quoted substring in the LogsQL query, whose filters come from identifiers validated for the caller's organization.
  - The API answers one deployment's build output with `environment.read`: `GET …/applications/{applicationId}/deployments/{deploymentId}/build-output` takes `from` (with its offset, in the past; an hour before the deployment started by default, since the agent stamps its lines with its own clock) and `limit` (500 by default and at most). It answers `kept` and `lines` oldest first, each with its `time`, `line` and `truncated`; a deployment of another application is not found. The deployment page reads it every three seconds while the deployment runs and twice more once it has finished, from three seconds before its last line (batches of one build may reach the store side by side), and again at once while an answer is full; it shows a line read twice once, keeps the last 8192 lines and follows the end unless the reader scrolled up.
  - Access is checked in a short transaction, the log store is read with no transaction and no account lock held, and access is checked again before a line is returned: a slow store never holds the account's lock, and access lost during the read returns nothing (issue #488).
- Metrics (ADR 0024): CPU, memory and network per container and per node, disk per node; HTTP request rate, mean latency and responses by status class (2xx, 3xx, 4xx, 5xx, other) per route from Caddy. Retention 30 days. Disk per container, the size of its writable layer, is what the disk budget measures (ADR 0022); it is not in the metrics report yet.
  - Every 30 seconds the agent samples:
    - the node: CPU in use, memory in use and in total, disk in use and in total under Docker's data root, and network bytes received and sent;
    - each managed container: CPU in use, memory in use and its limit, and network bytes received and sent;
    - each host name of its routes, from Caddy's `/metrics` with `per_host`: requests by status class, and the sum and count of response durations. Caddy labels a request with its `Host` header as sent, so every Shipkeep route matches it only as the route's name, alone or with port 443 or 80, and the agent adds that matcher to routes earlier agents wrote. Over HTTPS, `name:443` gets a label of its own, which the agent counts under the name. Over plain HTTP (a route with TLS off), Caddy labels a request whose `Host` carries a port `_other`, which the agent leaves out: those requests are not counted. `per_host` applies to all of Caddy's HTTP servers, so it is on only while every route of every server has matchers, names literal hosts (no wildcard, no placeholder) and carries that matcher (it is turned off before a wildcard route is written); otherwise the node reports no route metrics, since clients could choose the labels.
  - It sends them as a `MetricsReport` on the `Connect` stream, with the session's lease epoch. A report holds at most 256 containers and 64 host names: past those bounds each sample takes the next ones in name order, so every container and host name is reported at least once every ceil(count / bound) samples, and the node's values are never left out. At those bounds a report stays well under 60 KiB; one that would not is not sent. Nothing is kept while the stream is down.
  - The control plane refuses a stale epoch and ignores a report that breaks a bound.
  - It maps each container name to the node's placed allocation, and each host name to a domain whose application has a placed allocation on that node. It drops what maps to nothing, including a host name routed only on another node. It writes the samples to VictoriaMetrics with labels it sets itself: organization, project, environment, application, node, and either replica and container (the allocation's container name, which tells apart the old and new release of a replica during a rollout) or domain. A label the agent sent is never written as it came: the container label is the name the control plane recorded, which the agent's name only selects. Counters (CPU seconds, bytes, responses) are bounded by the largest exact integer, gauges (memory, disk, cores) by 1 PB.
  - VictoriaMetrics is a service of the control plane's Compose project, on its internal network only, pinned by digest, with 30 days of retention. Only the API queries it, with identifiers it validated for the caller's organization.
  - Charts read 1 h, 24 h, 7 d or 30 d, with points every 30 s, 5 min, 30 min or 3 h. An application's charts need `environment.read`, a server's `node.manage`. `GET /organizations/{organizationId}/metrics` gives the organization's requests by status class and their mean duration, step by step, with the total requests and mean response time over the whole period read at its end (the steps lag by up to one step), to any member: owners and admins read every environment, another member the environments `observability.read` allows, found by walking the organization's environments in pages until 100 readable ones are named or every environment was checked, and a member with none reads no series. `partial` is true when the walk stopped first, at 100 readable environments or after checking 2 000: the values then cover only a part. Requests have no percentile: a report carries counts and duration sums per host, not histograms.
  - Like a log search, a chart is authorized before and after its reads of VictoriaMetrics, which hold no transaction and no account lock. The organization's chart is refused when an environment it read is no longer readable when it answers (issue #488).
  - The API reads them back over a period of `1h`, `24h` or `7d`. `GET …/applications/{applicationId}/metrics` needs `environment.read` and gives CPU in cores, memory in bytes, requests per second by status class, and the mean response time. `GET /organizations/{organizationId}/nodes/{nodeId}/metrics` needs `node.manage` and gives CPU, memory, disk and network. Without `VICTORIAMETRICS_URL`, both answer `kept: false` with empty series, and the stream's Welcome tells agents to send no metrics.
- Alert rule types for MVP: container restarts, unhealthy instances, node suspect or down, CPU or memory above threshold for a window, disk usage above threshold, backup failed, certificate expiring in under 14 days, deployment failed.
- Channels: email (SMTP), Slack, Discord, Telegram, generic webhook (HMAC signed).

- Input: Coolify instance URL and API token (read scope), or a Coolify instance backup file.
- Imports: projects, environments, applications (git source, branch, build pack mapped to `build.type`), environment variables (as secrets by default), domains, managed databases (definition only, plus optional data migration through dump and restore).

## 14. Installation and upgrades

- M8.3a installs fresh Ubuntu 24.04 amd64/arm64 nodes. The HTTPS Servers screen displays a command that downloads a content-addressed installer into a private temporary directory, checks its SHA-256 before executing it, and pins both agent architectures. `web:build` builds those artifacts locally; no unsigned `curl | sh` or unpublished release URL is used. Checksums trust the authenticated control-plane origin; independent release signatures follow in M8.2. The token is read silently from stdin only after package and binary validation, saved as a 0600 file under the agent-owned 0700 `/etc/shipkeep`, then consumed by enrollment.
- Docker (when absent) and Caddy are installed from their signed upstream apt repositories, with pinned signing-key fingerprints. A downloaded key file that holds anything besides the pinned key is refused, and the keyring given to apt holds that key alone. Ubuntu's universe build of Caddy is not used: it is an old version with no guaranteed security updates. Existing Shipkeep paths/accounts, an existing Caddy, occupied HTTP/TLS ports and incompatible Docker daemons cause failure. This is an initial installer, not an upgrade or automatic cleanup tool. Docker signing keys are staged in a private directory under `/tmp`. Both the download and offline-application steps use the default APT cache. If Docker repository setup or package download fails (including SIGHUP or SIGTERM delivered to the package-download process), the installer removes the Docker apt source and keyring it created during the attempt only while they still identify its staged files. After downloads succeed, it conservatively keeps the signed repository for the offline APT step so Docker can receive updates even if a later package step fails. This also covers package-plan, cache or lock failures before dpkg starts: an APT error alone is not proof that no packages changed. An existing repository is refused with instructions to reconcile both files and remove leftovers only when they are confirmed to predate package application. If package application may have started, keep the repository, repair the package state, finish installing all Docker packages (including Compose for the control plane), and verify the daemon before retrying (INSTALL troubleshooting). If only the parent installer was terminated, wait for apt-get and dpkg to stop before retrying. A hard stop may leave its signing-key workspace; the logged workspace path identifies the exact directory to remove after confirming the stopped attempt, without touching other runs. The agent runs as `shipkeep`, with Docker access and no Linux capabilities (WireGuard adds its own with M4.1). Caddy runs separately without Docker access, with persistent autosave storage, `--resume` and the group-restricted Unix admin socket.
- The installer never rewrites existing Docker daemon configuration; it reports conflicts (ports 80 and 443 in use) and stops with instructions.
- The control plane is installed from a release bundle, `shipkeep-control-plane_<version>.tar.gz`: `install.sh`, `compose.yml`, `Caddyfile`, `.env.example` and an `image` file that names the release by tag and digest. `release.yml` builds it once the image is pushed, signs it and attaches it to the release. The installer checks the machine before it changes anything (root, free ports 80, 443 and 7443, a DNS name that resolves, no earlier installation and none of its Docker volumes), asks its questions (next item), installs Docker from its signed repository on Ubuntu 24.04 when absent, writes the settings with two generated database passwords, starts the stack and waits for HTTPS with a valid certificate. It is an initial installer: it does not upgrade, and cleanup after a failed run is limited to the apt files it created while installing Docker.
- The installer asks for the DNS name, then for the email address and the password of the first account (ADR 0020), and for nothing about email unless `--smtp-host` is given. Once the stack is up it creates that account with `node main.js account create`, the password on standard input. The password is never an option, a variable of a container or a line of `.env`. Both answers are checked before anything is installed, with rules no wider than the control plane's, so that the account is not refused once the stack runs: 15 to 128 Unicode code points of well-formed UTF-8 on one line for the password, and for the address a name of letters, digits and `_ % + -` joined by single dots, then a domain of at least two labels. A password line that holds a NUL byte or is not UTF-8 text is refused, never shortened or changed; a CR just before its line end belongs to that end, as the command line reads it; the command line of the control plane refuses a line that is not UTF-8 too, instead of replacing what it cannot read. The installer starts from its own variables: it unsets the names it keeps passwords under, which would stay exported to child processes if inherited, and the names Docker Compose would prefer to the settings file and the bundled compose file (the variables of the compose file, and every `COMPOSE_*` setting: `COMPOSE_DISABLE_ENV_FILE` alone would make it ignore `.env`). If the creation fails, the installer says how to run it by hand and exits with an error while the control plane keeps running.
- Channels: `stable`, `lts` (from v1), `edge`. Upgrades are manual by default with one click, automatic only if enabled.
- Upgrade procedure as in ARCHITECTURE section 5.

## 16. Open questions

- Writing a Git application's shipkeep.yml back to its repository (#214) takes a browser session only, the more cautious choice: an API token with `deploy.run` cannot write to GitHub through the organization's App yet. Whether the CLI should, and with which extra check, is still to be decided.
- A build in progress is bounded in time and memory but not in disk: BuildKit's garbage collection only frees its cache between builds, so a very large build can fill a disk it shares with the applications. A dedicated filesystem or a quota for `/var/lib/shipkeep-build`, or a watch that stops the builder before the disk fills, is still to be chosen.
- A Railpack build copies the repository to the server's disk for the build's time (ADR 0030), outside BuildKit's disk bounds: like the build itself, it has no disk bound yet.
- Builds on one machine installed before builds: `--migrate yes` adds the builder to an application server, but refuses a machine that also hosts the control plane, so such a machine gets no builder yet. Until a migration covers it, its builds fail with `builder_unavailable`.

- Installation-level audit access: system and account events (`organization_id` null, for example `fleet.installation_key.created`) are not readable by the runtime role. Proposal for M2.4a: an installation-administrator capability, held by the first owner and audited, with its own read context.

- Retry-safe certificate renewal after a response is lost: a recovery protocol must preserve the one-active-certificate invariant without accepting a revoked identity.

- Agent action history (issue #263): actions queued before the migration that links actions to deployments stay unlinked, because no released version has such actions to backfill. The agent sends the same `action deadline exceeded` text when it refuses an overdue request and when an action times out while running, so both are reported as `failed`; a distinct refusal text in the agent would let the history show the first as `refused`.

- Resource limits (issue #301). Reservations equal limits, so with the defaults a node runs as many applications as it has CPUs, unless they declare less. Still open:
  - a reservation smaller than the limit, quotas per environment, and capacity kept back for the node's own services (agent, Caddy, Docker);
  - `deploy.strategy: recreate`, which would stop the serving release first and avoid the overlap described in section 6: the pipeline always starts the new release next to the old one;
  - health check and release durations outside what the agent accepts, for example a release timeout above one hour, pass validation and fail when that step runs;
  - containers created before the limits became mandatory keep running without them, with a reservation of zero, until their application is deployed again.

- Deleting an application (issue #256) needs `environment.update`, because the permission catalog has no `application.delete`. A dedicated permission would let a role delete applications without changing environment settings, at the cost of a change to the role model and to API token scopes.

- Private registries: an organization can store credentials (ADR 0019). Still open: an explicit allow-list for registries on private networks (the resolver and the node's egress proxy refuse non-public addresses, SSRF, ADR 0023), and credentials scoped to a project.
- Cloning an environment that holds a Git application (#213): a copy would follow the same branch, and the repository's next configuration would bring back the domains the original serves. The clone is refused until a copy can follow another branch.
- Corrosion adoption for peer-to-peer routing replication (target v0.5).
- Wildcard certificates: which DNS providers to support first for DNS-01 (proposal: Cloudflare, Route 53, Hetzner DNS, OVH).
- The agent of a separate control plane machine (ADR 0028) needs Ubuntu 24.04 with systemd and Docker API 1.47, like every server, while the control plane alone runs on any Linux with Docker. The installer keeps both: elsewhere, or with an older Docker, it installs no agent and creates no organization, even with `--organization`, and that control plane is upgraded by hand. Requiring Ubuntu 24.04 for every control plane machine would give every installation the upgrade from the web interface.
- Node public addresses (PLAN M3.6b1) are declared by an administrator only. The gateway sees the source address of each agent connection, but behind NAT, a proxy or a private link that is not the address visitors reach, so it is not used. A later step could show the observed address as a suggestion that an administrator confirms, never as a stored value.
